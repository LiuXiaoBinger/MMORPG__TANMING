# 客户端角色脏标记设计方案

## 1. 设计目标

客户端需要知道“哪些角色数据发生了变化”，从而只刷新受影响的界面、重算受影响的派生属性，并让不同模块在角色切换和断线后正确清理自己的状态。

这里的“脏”是客户端运行时概念，不是服务端持久化概念。它表示某个客户端模型最近发生过变化，不能表示数据需要发给 CenterServer，也不能替代服务器的权威校验。

本方案适用于当前项目的角色组件化结构：

- `ClientRole` 是客户端角色数据根对象。
- `RoleWorldSystem.LocalRole` 是当前玩家角色的唯一入口。
- 角色业务数据放在角色组件中，例如 `RoItemComponent`、`RoleCountComponent`。
- 网络协议由 `MainCtrl` 等控制器接收，再交给对应角色组件。
- UI 只通过 Controller/ViewModel 读取组件数据，不直接解析协议。

## 2. 当前问题

当前项目已经有两种通知方式，但还没有统一的角色级变更聚合：

| 模块 | 当前通知方式 | 现状 |
|---|---|---|
| 背包 | `KnapsackChangedDetailed` | 已支持新增、删除、数量变化、移动和容量变化的细粒度刷新 |
| 次数 | `RoleCountComponent.CountChanged` | 已支持商城限购、副本次数等变化通知 |
| 角色基础信息 | 直接更新角色协议对象 | 缺少统一变更事件，外部直接修改可能绕过通知 |
| 装备、技能、Buff、任务 | 尚未统一 | 后续需要接入统一脏位和领域事件 |

如果每个模块都自行维护一套刷新标记，会出现重复刷新、事件订阅难以释放、切换角色后旧角色继续驱动 UI 等问题。因此需要一个轻量的角色级脏标记聚合层，但不能破坏背包已有的细粒度事件。

## 3. 核心原则

### 3.1 服务器仍然是最终权威

服务器回包到达客户端后，客户端只负责应用服务器数据和刷新显示。客户端脏标记不参与伤害结算、购买结算、扣款、限购判断或服务器保存。

### 3.2 脏位表示领域，不表示具体对象

脏位只回答“哪个领域发生了变化”，例如背包、次数、装备、技能、Buff、任务、基础属性。具体变化由领域事件或变更快照描述。

例如：

- `Bag` 脏位表示背包模型有变化，具体是哪个 UID、哪个格位由背包变更事件提供。
- `RoleCount` 脏位表示次数模型有变化，具体是哪个行为和业务编号由次数变更事件提供。

### 3.3 一次网络回包可以产生多个领域变化

一次商城购买可能同时产生：

- 商品进入普通背包；
- 虚拟物品数量减少；
- 商城购买次数减少。

协议处理器应先更新对应组件，再由组件分别发布领域变更。不能把所有逻辑塞进商城 UI 或 `ShopMgr`。

### 3.4 同一帧只合并通知，不丢失最终状态

同一帧内多次修改同一领域时，可以只让 UI 刷新一次，但组件内部必须保留最终数据。对于背包这种需要 UID、旧格位和新格位的信息，仍保留细粒度事件，不用整页重建。

### 3.5 角色生命周期必须隔离

角色切换、断线、重新登录时，必须先取消旧角色的事件订阅，再绑定新角色。旧角色的事件不能刷新当前角色界面。

## 4. 推荐分层

```text
网络协议回包
    |
    v
MainCtrl / 领域协议处理器
    |
    v
ClientRole 的对应角色组件
    |                 \
    |                  +--> 细粒度领域事件
    v                           |
角色脏标记聚合器                 v
    |                       领域 Controller
    v                           |
本帧批量变更通知                  v
    |                         ViewModel
    v                           |
派生属性重算 / 缓存失效       UI 局部刷新
```

### 4.1 `ClientRole`

职责：

- 持有角色协议数据和角色组件；
- 提供组件查询；
- 持有角色生命周期状态；
- 持有角色级脏标记聚合器；
- 在角色销毁时统一清理组件和事件。

不负责：

- 解析具体协议；
- 直接操作 Unity UI；
- 连接 GateServer 或 CenterServer；
- 复制一份商城、背包或次数数据。

### 4.2 角色组件

每个组件拥有自己的权威客户端模型，并在应用服务器快照或增量后发布变化：

- `RoItemComponent`：物品容器、虚拟物品、装备栏和背包事件；
- `RoleCountComponent`：商城购买次数、副本次数等次数数据；
- `RoleAttributeComponent`：角色基础属性和派生属性；
- `RoleEquipComponent`：穿戴栏、装备属性和装备变化；
- `RoleSkillComponent`：技能学习、等级、冷却或技能配置状态；
- `RoleBuffComponent`：Buff 列表、开始时间、结束时间和服务器时间校正；
- `RoleTaskComponent`：任务状态和任务进度。

组件的统一约定：

- 应用服务器数据后再发布变更；
- 不在事件中暴露可变协议对象或可变内部容器；
- 事件参数使用不可变快照或基础值；
- 清理时取消事件并释放内部引用；
- 不使用 `foreach` 和三目运算符；
- 关键状态和复杂变更必须有中文注释。

### 4.3 脏标记聚合器

建议作为 `ClientRole` 的角色级子对象，名称可采用 `RoleDirtyState` 或 `RoleDirtyTracker`。它只做三件事：

1. 接收组件报告的领域变化；
2. 合并同一帧内重复领域的脏位；
3. 在控制器需要时取出并清除本帧变化。

它不保存第二份业务数据，也不负责刷新 UI。

建议的领域脏位：

| 领域 | 用途 | 当前接入情况 |
|---|---|---|
| `Bag` | 普通、装备、消耗品、材料、虚拟物品和穿戴栏 | 已有细粒度事件，脏位只做聚合标记 |
| `RoleCount` | 商城限购、副本次数 | 已有 `CountChanged`，增加领域聚合 |
| `RoleAttribute` | 等级、生命、攻击、防御等 | 待接入 |
| `Equip` | 装备穿戴、卸下、强化属性 | 待接入 |
| `Skill` | 技能列表、技能等级、冷却状态 | 待接入 |
| `Buff` | Buff 增删、层数、剩余时间 | 待接入 |
| `Task` | 任务状态和进度 | 待接入 |
| `Social` | 好友、公会、邮件等角色相关社交数据 | 后续接入 |

## 5. 一次变化的完整流程

以商城购买为例：

1. `MainCtrl` 收到购买结果或物品、次数同步协议。
2. 控制器把物品增量交给 `RoItemComponent`，把次数增量交给 `RoleCountComponent`。
3. `RoItemComponent` 更新虚拟物品或商品实例，然后发布背包细粒度事件，并报告 `Bag` 领域变化。
4. `RoleCountComponent` 更新商品购买次数，发布 `CountChanged`，并报告 `RoleCount` 领域变化。
5. `ShopCtrl` 收到次数变化或商城模型变化通知，只更新受影响商品的限购文本和按钮状态。
6. `KnapsackCtrl` 收到背包细粒度事件，只刷新受影响格子；数量变化只刷新数量文本，移动变化刷新旧格和新格。
7. 本帧结束时，脏标记聚合器可用于统一触发派生属性重算或缓存失效，但不再次重建整页 UI。

## 6. 脏标记的状态模型

每个领域至少需要三个状态概念：

| 状态 | 含义 |
|---|---|
| `Clean` | 当前模型和相关 UI 缓存没有待处理变化 |
| `Dirty` | 组件模型已变化，等待控制器处理或本帧批处理 |
| `Applied` | 控制器已经处理本次变化，领域回到清洁状态 |

实际实现时不建议为每个领域保存递增的大版本号。客户端脏标记只需要短生命周期的本地序号或帧序号，避免把它误解成服务端 `save_version`。

建议同时保存：

- 当前角色实例标识，用于隔离旧角色事件；
- 当前帧或本地变更序号，用于合并同帧事件；
- 领域位集合；
- 每个领域待处理的不可变变更摘要。

## 7. 事件和脏位的关系

脏位与领域事件不是互相替代，而是两个层次：

- 领域事件回答“具体改了什么”；
- 脏位回答“哪些领域需要处理”。

推荐规则：

- 背包、次数等已有高质量增量事件继续保留；
- 脏位只作为跨模块聚合和批处理入口；
- UI 需要精确刷新时使用领域事件；
- 派生属性、缓存和统计汇总使用脏位；
- 没有具体增量信息的模块才使用领域快照刷新。

## 8. 模块接入建议

### 8.1 背包模块

背包不应因为加入脏标记而改成整页刷新。保持当前设计：

- `RoItemComponent.ApplyServerItemDelta` 应用服务器增量；
- `KnapsackChangedDetailed` 发送 UID、类型、旧格位、新格位和数量；
- `KnapsackCtrl` 更新缓存并调用 `RefreshSlot`；
- `RolePackPlain` 继续保持独立，不汇总其他背包；
- 虚拟物品仍属于 `RoleVirtualItemPack`，商城货币显示从虚拟物品组件读取。

脏位在背包模块中只用于：

- 标记背包统计需要重新计算；
- 标记货币摘要或装备属性缓存失效；
- 同帧内合并多个背包变更。

### 8.2 次数模块

`RoleCountComponent` 接收 `CountUpdateSyncInfo` 后：

- 按行为类型和业务编号更新本地次数；
- 触发 `CountChanged`；
- 标记 `RoleCount` 领域脏位；
- `ShopCtrl` 只刷新对应商品的限购显示。

购买回包本身只负责成功或失败提示，不能让 `ShopMgr` 再计算、扣除或覆盖次数。

### 8.3 装备模块

装备穿戴可能同时影响装备栏、背包格位和角色属性。建议按顺序：

1. 装备组件应用服务器结果；
2. 背包组件处理跨容器移动；
3. 属性组件重新计算派生值；
4. 分别报告 `Equip`、`Bag` 和 `RoleAttribute` 脏位；
5. `RoleInfoCtrl` 和 `KnapsackCtrl` 只刷新各自受影响的 View。

### 8.4 Buff、技能和任务模块

这些模块优先使用领域事件：

- Buff：增删、层数、开始时间、结束时间；
- 技能：技能 ID、等级、冷却结束时间；
- 任务：任务 ID、状态、进度。

脏位只用于提醒控制器或派生系统存在变化，不把完整模块数据复制到 `Global` 或某个 UI 管理器中。

## 9. 网络回包处理边界

网络处理器只负责解析和路由：

- `MainCtrl` 注册协议入口；
- 协议回包解析为 protobuf 对象；
- 找到当前 `LocalRole`；
- 调用对应组件的 `ApplyServerSnapshot` 或 `ApplyServerDelta`；
- 组件负责修改模型和发布事件。

禁止以下做法：

- 在 UI View 中直接解析 protobuf；
- 在 `ShopMgr` 中保存一份货币或购买次数；
- 在客户端购买成功回包中自行扣钱或增加购买次数；
- 用客户端脏位调用服务器保存接口；
- 收到一个背包变化后重建所有页签和所有格子。

## 10. 角色切换、断线和重连

### 角色切换

1. 控制器解除旧 `ClientRole` 的所有组件事件订阅；
2. 清空控制器自己的 ViewModel 缓存；
3. `RoleWorldSystem` 设置新的 `LocalRole`；
4. 控制器绑定新角色组件；
5. 新角色完成登录快照后，再执行一次必要的完整刷新。

### 断线

- 停止接收旧连接代次的业务回包；
- 清理当前角色的临时脏位和待处理 UI 事件；
- 不删除可复用的配置缓存；
- 重连成功后以服务器完整快照重新建立角色组件状态。

### 旧回包隔离

购买、次数和物品回包必须通过连接代次或当前角色实例校验。旧连接回包即使协议解析成功，也不能写入新角色。

## 11. 与服务端保存版本的区别

| 项目 | 客户端脏标记 | 服务端保存版本 |
|---|---|---|
| 作用 | UI、缓存和派生计算 | CenterServer 持久化幂等和 ACK |
| 权威方 | 当前客户端模型 | GameServer / CenterServer |
| 生命周期 | 通常按帧或控制器处理后清除 | 由服务端持久化链路确认 |
| 是否发送给服务器 | 不直接发送 | 作为保存请求版本发送 |
| 是否能决定业务结果 | 不能 | 不能绕过业务校验，但决定保存顺序 |

客户端不要复用 `save_version` 作为 UI 脏位版本，也不要把客户端本地序号写入服务端协议。

## 12. 推荐实施顺序

1. 保留 `RoItemComponent` 和 `RoleCountComponent` 现有细粒度事件，先定义统一领域名称。
2. 在 `ClientRole` 中增加轻量脏标记聚合对象，只接收领域变更报告。
3. 给角色基础属性增加受控更新入口和变更事件，禁止外部直接修改关键字段。
4. 接入装备、技能、Buff、任务组件的快照/增量事件。
5. 在 `MainCtrl` 或角色运行时更新入口中增加同帧批处理点。
6. 为每个 Controller 增加角色绑定和解绑检查，覆盖切换角色、断线和重连。
7. 用测试组件验证同帧合并、事件只触发一次、旧角色事件隔离和非可见背包格缓存更新。

## 13. 验收标准

- 购买商品后，道具、虚拟货币和购买次数分别进入各自组件；商城限购只刷新对应商品。
- 同一帧连续修改同一模块，UI 不重复整页刷新。
- 背包新增、删除、数量变化和移动仍保持当前细粒度刷新行为。
- 角色切换后旧角色事件不会刷新新角色界面。
- 断线重连后以服务器快照恢复，旧连接回包不会污染新角色。
- 客户端脏位不会进入服务器保存协议，也不会改变服务器权威结算。
- 正式业务代码不增加测试按钮、Mock 数据、`foreach` 或三目运算符。

## 14. 结论

客户端应采用“角色级脏位聚合 + 模块级细粒度事件”的组合方案：

- 角色组件保存数据；
- 组件发布具体变化；
- 角色级脏位做跨模块合并；
- Controller 将变化转换成 ViewModel；
- View 只负责显示；
- 服务器回包始终覆盖客户端预测状态。

这样既能承接商城、背包、装备、任务、技能和 Buff，也不会把所有逻辑重新集中到一个大型管理器中。
