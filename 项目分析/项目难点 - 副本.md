### 先把术语说成人能理解的话

| 术语 | 含义 | 项目里具体的例子 |
| --- | --- | --- |
| 技能核心Core | 角色已学某技能的配置与运行信息，能被多次施法使用 | Q对应10010，每按一次仍使用这个已学技能核心 |
| 单次技能实例 | 某一次施法的独立对象，保存该次时钟、表现段和资源操作 | 连按两次Q是同种技能，但应该有两个不同的施法身份 |
| 预表现 | 请求提交后客户端先播放动画等反馈，尚待权威结果 | 按Q后先出招，服务器拒绝时再停止对应表现并校正状态 |
| 权威结果 | 服务端根据真实角色数据计算的接受/拒绝及MP/CD | 客户端不能靠改本地蓝量让服务器免扣费 |
| 动作窗 | 当前技能占用角色动作状态的时段 | 窗口到期后允许按规则切到下一动作，但旧声音可能还没播完 |
| 表现尾段 | 动作退出后仍在继续的粒子、声音或制作事件 | 出刀结束之后，刀光消散和声音尾部仍需继续 |
| 根运动 | 动画提供角色根节点位移增量 | 滑步动画除了改变骨骼姿态，还提供角色前移的距离 |
| 影子目标 | 远端收到服务器通知后保存的目标位置 | B收到A的新位置，使用该目标推动A在B端的表现 |
| 冷/暖资源 | 尚未加载/已经加载可用的资源 | 首次施法模型未齐是冷路径，再次使用已加载模型是暖路径 |
| Shader变体 | 同一Shader在不同关键词和通道组合下的编译版本 | 同样的透明特效Shader，启用发光与UV噪声时需要对应组合 |
| 热更DLL与AOT主包 | 可更新的业务程序集与安装包已有的原生编译依赖 | 更新GM_Game.dll能改业务；旧主包缺少的共享AOT类型不能只靠业务DLL补齐 |

术语解释完后再给类名，面试官才能理解这些类为什么存在。

## 项目介绍：先让面试官理解做了什么

### 30秒介绍

这是一个基于Unity 2023.2和C#开发的3D MMORPG项目。客户端使用YooAsset和HybridCLR管理资源与代码热更，服务端采用Login、Gate、Game、Center四类服务，使用TCP和Protobuf通信，Luban管理前后端配置。项目重点围绕技能释放、动画与位移、技能编辑发布以及多角色同步打通完整链路，其中技能系统参考RO的职责划分，按当前项目需要做适配。

### 2分钟展开

这个项目主要围绕三个问题展开。第一，技能操作需要及时反馈，同时学习等级、蓝量和冷却必须由服务器校验。为此客户端把长期技能核心和单次施法实例分开，通过施法UUID关联预表现与服务器结果；服务器统一验证并提交MP、CD和施法状态。

第二，动画、特效、声音和位移需要按同一次施法协调。项目保留统一技能入口，编辑器负责制作和导出已支持的表现数据，运行时按技能时钟注册事件，动画水平根位移与程序位移最终经过统一碰撞移动。动作退出、服务器结束和表现尾段分别管理，避免接段时截断旧特效，也避免旧动作继续推动角色。

第三，编辑器看起来正常不代表打包运行正常。项目将作者配置、导出配置、资源清单、真实Bundle和热更程序集逐层核对，并结合实际Animator和固定条件渲染定位问题。已排查过远端技能播完才补移、技能退出瞬间下沉和包内特效变白框等问题，修复尽量落在真实缺口，保留原接口和已工作的流程。

以上是当前实现与排查经验。完整目标伤害、服务器物理移动权威、动态AOI和大规模并发压测尚不能作为已完成成果；个人介绍时补充自己实际承担的模块。

## 系统结构与关键业务链路

| 层次 | 当前职责 | 面试时需要讲清的边界 |
| --- | --- | --- |
| Unity客户端 | 输入、角色实体与组件、技能预表现、动画/粒子/声音、远端移动表现 | 本地预表现不等于服务器接受；移动当前位置来自客户端碰撞链 |
| Login / Gate | 登录接入、连接会话及协议转发 | 会话用于定位真实角色，请求不能任意指定他人的权威身份 |
| Game | 在线角色、技能状态、MP/CD、附近角色广播，20Hz固定步长业务更新 | 固定Tick不等于客户端锁步帧同步，也不代表完整战斗玩法已接入 |
| Center / 配置层 | 角色与学习数据装载等业务，Luban提供主表/等级效果/表现数据 | 编辑器表现数据不改写服务器学习等级、费用和冷却 |
| 制作与发布工具 | 作者配置、导出校验、运行表现、依赖验证、热更资源 | 编辑器“保存”与发布Runtime是不同步骤，最终运行版本还需核对实际产物 |

技能释放的主线：

```text
技能输入 → MSkillClassicsHandler → MWaitingDataMgr → MNavigationComponent
        → 上报已有位置 → CanStart → 发送SkillCastReq → 本地BeginPrediction
Gate转发 → Game逻辑线程 → SkillCastHandler → ROSkillComponent.TryCast
        → 验证学习/状态/MP/CD → 提交成功结果 → 附近Start/End通知
客户端  → UUID匹配已有预表现或创建远端实例 → 权威MP/CD校正与生命周期收尾
```

在线发送路径按现有接口完成请求提交后开始预表现，不等待服务器确认；同步发送抛错时不启动本次表现。提交成功只说明发送接口完成，不能讲成服务器已收到或已接受。导航模块目前是即时交接入口，不能讲成已经实现了寻路追近。

技能制作的主线：

```text
SkillConfigSO作者配置 → SkillEditorBinding绑定既有表现身份
→ 校验并导出SkillRuntimePresentation → YooAsset收集与Bundle构建
→ MSkillFactory/MSkillCore装配 → MArtSkill.FireEvents注册计时器
→ 到期分派粒子/声音 → 模型未加载时按该条操作等待GO回调
```

本节源码入口：

- `LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Component/MNavigationComponent.cs`
- `LYF_Server/GameServer/MessageHandler/Skill/SkillCastHandler.cs`
- `LYF_Server/GameServer/Components/ROSkillComponent.cs`
- `LYF_MMO/Assets/GM_Game/Editor/Skill/SkillEditorAssetTools.cs`

## 核心亮点：按业务价值讲实现

| 优先级 | 亮点 | 能体现的能力 | 深入案例 |

| 主讲 | 技能核心、单次施法和服务器校验分层 | 状态职责、交互响应、权威数据与异步生命周期 | 难点四 |
| 主讲 | 技能编辑、发布和运行表现衔接 | 工具与业务集成、数据契约、资源依赖 | 难点三、四 |
| 主讲 | 普通移动与技能位移统一提交 | 动画、网络表现、碰撞及坐标所有权 | 难点一、二 |
| 服务端重点 | 网络线程与游戏状态处理分离 | 并发边界、协议分发、固定步长时钟 | 难点五 |
| 工程加分 | 资源与代码热更链路可核对 | 实际产物定位、环境差异、版本一致性 | 难点三 |

### 亮点一：技能系统把配置、施法和权威状态分开

**解决的问题**：同一个技能有多个等级和表现段，每次施法又有独立的UUID、动作时钟、异步回包和尾部表现，全部塞到一个控制器会造成状态相互覆盖。

**具体实现**：`MSkillFactory`按学习等级和职业装配`MSkillCore`；核心保存对应配置和技能能力，`MSkill/MArtSkill`保存某一次施法的身份与表现生命周期，`MSkillComponent`协调当前动作、旧施法和冷却。服务器真实在线入口使用`ROSkillComponent → RoleSkillComponent`，由会话找到角色，按服务端学习等级解析效果，校验通过后才扣MP、登记CD和创建活动施法；客户端按UUID确认已有预表现，避免广播再次启动同一动作。

**价值与取舍**：保留RO可读的职责和命名，同时接入本项目真实OnlineRole与Unity模型，避免复制一套没有消费者的框架。预表现降低等待网络结果的体感，权威结果校正MP/CD；这属于施法预表现和结果校正，不是确定性战斗回滚。

**面试一句话**：技能系统的重点是把“某个技能的配置”和“这一次施法的状态”分开，让客户端及时反馈、服务器控制准入与消耗，并正确处理回包和旧表现。

依据：`项目分析/RO_SKILL_COMPONENT_PARITY.md`、`项目分析/RO_SKILL_OBJECT_POOL_AUDIT.md`。

### 亮点二：制作工具与正式技能播放器有明确契约

**解决的问题**：可视化时间轴容易让制作端自由度超过运行端支持范围，或者为了预览再给正式角色挂另一套播放器，导致动画和根运动争用。

**具体实现**：基于已有YCombatEditor制作界面接入宿主项目，保留`SkillEditorWindow/SkillConfigSO`，通过`SkillEditorBinding`映射既有表现身份。保存作者资产后需显式校验导出，生成运行表现；`SkillEditorAssetTools`核对原表、动画时长和宿主支持字段。已接入动画、粒子、声音与动画位移窗口等表现数据，运行仍走`MSkillComponent → MSkill/MArtSkill → MAnimator`。五种粒子定位由宿主定义，不能只靠窗口里看得到轨道就认为该轨道已被正式执行。

**价值与取舍**：复用成熟编辑界面，集中实现宿主数据转换与运行契约。表现制作与权威数值分离，编辑器不修改服务端消耗和学习规则；不把第三方窗口及所有轨道说成全部自主研发或全部接入。

**面试一句话**：工具层重点做的是从作者配置到运行数据的受控发布，让编辑器能制作的内容和游戏真正会执行的内容对应起来。

依据：`项目分析/SKILL_EDITOR_CODE_READING_GUIDE.md`、`项目分析/YCOMBAT_EDITOR_INTEGRATION_USAGE.md`。早期文档七份表现是历史，本次已有八份正式Runtime，不能背成固定七份。

### 亮点三：位移有统一消费者，远端沿目标位置追赶

**解决的问题**：输入移动、技能根运动、程序位移和网络追赶同时作用时，容易出现双倍位移、角色动画与坐标不一致、技能结束补走旧距离。

**具体实现**：本地移动后按位置/朝向/移动状态变化及既有节流上报终点和耗时；服务器更新现有在线角色位置，向同图附近玩家广播。远端通过`onSyncMoveEvent/LagSyncUpdate`追赶影子目标。根采集器只交付当前技能有效窗口中的水平动画增量，由`MMoveComponent`与其他位移合并提交碰撞；远端存在技能位移时避免再叠加普通追赶，并按实际落点重算残差。

**价值与取舍**：统一坐标写入，按实际碰撞结果维持同步残差。当前采用位置状态同步与影子追赶，保留RO正常流程；尚未实现输入历史重演、完整服务器移动模拟或完整动态AOI。

**面试一句话**：同步效果取决于位移的生产、消费和碰撞结果是否一致，不能只关注收包和插值公式。

依据：`项目分析/RO_MOVE_SYNC_CLIENT.md`、`项目分析/RO_MOVE_SYNC_SERVER.md`、`项目分析/SKILL_ROOT_MOTION_SYNC.md`。

### 亮点四：网络收包与GameServer状态处理分离

**解决的问题**：Socket回调来自网络线程，若直接改在线角色、背包或技能状态，就会出现并发读写，业务分发也容易堆成一个大switch。

**具体实现**：TCP使用两字节长度帧及现有封包格式，累积缓存循环取完整帧并保留半包，再反序列化Protobuf。回调把消息投递为`GameCommand`，总队列再交模块队列，主循环按来源与协议查注册处理器。两级队列是传递关系，不是同一命令执行两次。GameGlobal先处理网络阶段，再按50毫秒固定步长推进逻辑，每轮追赶最多5帧，未消费时间继续保留。

**价值与取舍**：明确游戏状态修改线程，协议解析/路由与领域规则分离，固定步长便于技能截止Tick与CD统一判断。现有队列容量和单轮消费限制是实现参数，不能当吞吐量压测结果；本地单线程提交MP/CD也不能夸大为跨服务数据库事务。

**面试一句话**：网络线程负责交付命令，游戏状态在主循环集中修改；固定Tick管理业务时间，协议Handler只承担入口适配。

源码：`LYF_Server/Network/Socket/com/ServerBase.cs`、`LYF_Server/GameServer/manger/Command/GameCommandDispatcher.cs`、`LYF_Server/GameServer/MessageHandler/ClientMessageManager.cs`、`LYF_Server/GameServer/GameGlobal.cs`。

### 亮点五：热更排查核对实际运行产物

**解决的问题**：编辑器修好后安装包仍报错，或资源清单看似齐全但特效渲染异常，仅检查源码和文件名无法确认当前客户端执行了什么。

**具体实现**：Boot经YooAsset完成初始化、版本/清单查询和下载，再加载热更程序集资源、补充AOT元数据、进入登录。非Editor路径实际`Assembly.Load`热更字节。排查时对真实包中TextAsset、正式DLL、方法IL及资源清单做核对；技能Runtime、动画与粒子依赖还需真实Bundle加载和渲染验证。

**价值与取舍**：能区分“源码已修”“程序集已更新”“资源已入包”和“安装包画面已验”四种状态，避免拿编辑器通过替代发布验收。YooAsset、HybridCLR是使用的第三方能力，项目亮点在集成与诊断，不在声称自研热更运行时。

**面试一句话**：排查热更问题要核对进程真正加载的程序集和真实资源包，源码改动本身不能证明客户端已经换版。

源码：`LYF_MMO/Assets/Boot/Load.cs`。依据：`项目分析/DEFAULT_ACTION_SHORT_CIRCUIT_RUNTIME_FIX.md`、`项目分析/SKILL_FX_PACKAGE_RUNTIME_DIAGNOSIS.md`。

### 亮点六：把故障现象拆成能验证的假设

**具体做法**：下沉按实体根与骨骼分层采样；特效按材质、纹理、Shader执行分层对比；不能施法则分别观察状态、时钟、CD和MP。修复前重现真实失败，修复后做针对回归，保留失败证据；有必要时再使用真实Animator、碰撞组件、实际Bundle或回环TCP验证。

**价值与边界**：能够解释为什么修改有效，以及验证尚未覆盖什么。源码专项、原生隔离、正式联机和安装包体验各自给出结论，不能累计历史断言数量充当性能收益或全量验收。

**面试一句话**：定位问题时先找到哪一层数据违背预期，再用最小修改和同条件实验验证因果。

## 把亮点讲透：按一次真实操作拆开说明

### 一、按一次Q，客户端与服务器各做什么？

**先说目标**：玩家按攻击键应尽快看到出招，但能否施法、用哪个等级、扣多少蓝和何时冷却结束，不能由客户端自行决定。项目当前打通的是技能准入、消耗与表现链，完整目标命中和伤害仍未接入。

**第一步：把“角色学会的技能”装配好。** 角色技能列表来自服务端装载的数据。客户端`MSkillFactory`根据技能ID、等级、职业读取Luban表：主表说明是什么技能，等级效果表提供MP/CD等规则，表现表说明这个职业模型要播什么动画。`MSkillCore`持有装配结果，按键时不用从头扫描全部配置。

**第二步：输入进入同一个释放入口。** Q由`SkillCtrl`交给`MSkillClassicsHandler.CastSkill`，再沿等待/导航模块交接。当前没有完整寻路，导航模块即时交接；先上传角色当前位置，再检查已学技能、跳跃/当前状态、MP和CD。客户端这次检查主要减少明知无法施法的输入，不替代服务端校验。

**第三步：生成单次身份，发包后启动预表现。** 请求携带`SkillId`与`SkillUuid`。在线路径发送接口完成后，`BeginPrediction`开始本地CD并创建这次施法的表现实例，交动作状态统一播动画。同步发送抛错时直接退出，避免该次空放。现有客户端为空时的本地路径是既有行为，不能把它描述成严格的在线提交确认；整个流程也没有增加等待服务器回复的输入锁。

**第四步：网关转发，Game逻辑线程校验。** `SkillCastHandler`从网关/客户端会话找在线角色；请求没有任意指定角色身份或技能等级。`ROSkillComponent.TryCast`依次检查装载、在线/存活、状态互断、学习等级、职业、配置、单CD/组CD及MP。新技能全部通过后才允许中断旧动作并提交消耗，拒绝请求不能提前扣费或推进下一段。

**第五步：成功时一次提交状态，再通知客户端。** MP按服务端当前等级效果扣除，单CD和组CD登记截止Tick，创建活动施法。处理器先返回结果，再向现有附近角色广播开始；自然到期/打断产生对应结束。该提交在单逻辑线程完成，当前不是数据库跨服事务。

**第六步：本人与旁观者处理不同。** A已按同一个UUID开始预表现，收到开始广播时确认这一次，不从头重播动画。B没有这次实例，按通知中的角色ID、效果ID、段号创建远端表现。RoleId用于找角色，UUID用于找施法，两者职责不同。

**第七步：回包校正MP/CD，并保护新输入。** 本地最新结果更新MP和公共组快照，匹配核心最新施法的结果更新单CD；拒绝停止对应实例。旧段迟到结果可以处理自己的旧表现，但不能覆盖新段的MP/CD，也不能重新启动一个已结束的旧动画。

**教学示例：解释接受、拒绝和旧回包。** 假设服务端A当前100蓝，Q费用20、本地刚提交UUID41。服务端接受后权威结果为80蓝；本地正在播的UUID41只被确认，B创建同一次表现。如果客户端误以为有蓝、服务器其实只剩10蓝，则返回不足，客户端停止UUID41的预表现并用10蓝校正。随后又提交UUID42时，UUID41的旧结果不能把最新蓝量改回旧值。这里100/10/41/42用于讲流程，实际蓝量取运行现场。

**CD为什么用剩余时间，而不直接比客户端系统时间？** 回包带服务器生成时间和CD截止时间，二者相减再转秒；之后用本地不缩放时钟倒计时。这样不会因为玩家电脑时钟快几分钟而算错截止。当前没有额外完整RTT补偿机制，不应宣称网络时延完全消除。

**可以直接讲给面试官**：

> 我把技能的即时反馈和最终许可分开了。玩家按Q后，客户端先做本地检查，提交带施法UUID的请求，然后开始动画和本地冷却。服务器根据会话找到角色，用真实学习等级检查蓝量和冷却，成功才提交消耗。回包回来时，同一个UUID确认已有动画，其他客户端则新建表现；拒绝时只停止对应那次施法。这样既不用每次等网络再出招，也不会让客户端决定费用。这个项目已经有准入和MP/CD权威，目标伤害还没有完成。

### 二、为什么Q能接三段，而旧刀光和声音不会立即消失？

**先区分“连续攻击”和“自动组合技”。** 本项目Q是同一个10010技能的三份动作表现，连续有效输入按段轮换；每次按键只释放一段，没有自动把三段打完，也没有缓存所有提前按下的按键。`UsingTimes`是选择表现的段号，不能把它讲成另一种新技能或复杂自动连招。

**一次接段同时出现三个对象关系。** 长期的Q核心选择当前段；UUID41的实例锁定自己那一段动画、状态时长和制作事件；等动作窗到期，角色允许按规则切到UUID42。UUID41可能仍在旧列表里持有刀声和粒子，但它已经失去角色动画与根位移的所有权，不能再推动角色。

**为什么需要两种时间？** 假设动作窗0.7秒、某个声音2秒结束，这是教学示例。如果等2秒才允许下一段，操作会被声音拖住；如果0.7秒把整个对象释放，声音被截断。项目把动作解锁、制作时间线和资源结束分别处理；Q已有700毫秒动作窗的历史配置依据，但声音长度必须以具体资源为准，不能把这个教学例子当所有技能统一配置。

**为什么要锁住当前段？** 服务端返回段号用于确认和后续选择；当前实例已锁定自己开始时的剪辑。否则前一段迟到回包修改核心后，正在播的新一段可能突然切回旧动画。服务器在成功请求后才推进段号，拒绝不能消耗一个段。

**为什么回池不清CD？** 这次动画/声音对象结束，只表示表现资源可回收，技能可能仍冷却数秒。CD记录由施法、权威结果、倒计时和明确清场管理。项目实际发生过表现实例回池时把10秒CD清成0的故障，详见后面的“问题八”。

**为什么需要对象持有关系？** 核心换等级后，字典会改用新核心，但旧施法可能仍引用旧核心。最后一个持有者解除前不能把旧核心放回池，否则其他技能借到它并重置字段，会污染还没结束的旧实例。对象池降低重复分配，但必须先解决这种所有权。

**参考差异也要说清。** RO普通轮换客户端使用10秒重置间隔、服务端使用6秒窗口，项目沿参考接入并用权威段号确认，不应口头说两个窗口完全一致。原方案中的旧协议名已被后续统一UUID链替代，讲当前入口和字段即可。

**可以直接讲给面试官**：

> 接段不是把前一次技能立刻销毁。项目把“还能不能占角色动作”与“旧表现是否播完”分开，动作窗结束就可以交出动画和位移，旧刀光和声音留在自己的实例里收尾。这样新一段能及时进入，旧声音又不会截断。最终回池只清表现资源，不清合法冷却。这里真正难的是多个生命周期和资源所有权，而不是简单把三个动画循环播放。

依据：`项目分析/RO_NORMAL_ATTACK_USING_TIMES_DESIGN.md`、`项目分析/RO_Q_COMBO_TEMPO_REFERENCE.md`、`项目分析/RO_SKILL_CD_LIFETIME.md`，以最终修订和当前源码为准。

### 三、编辑器拖动一条特效，怎样变成游戏里的技能表现？

**制作端和运行端各有一份数据。** 作者在`SkillConfigSO`中拖动动画、粒子、声音等轨道；绑定资产说明这份配置对应现有哪条表现。保存作者稿只保存制作数据；显式校验导出后才更新游戏读取的`SkillRuntimePresentation`。分开后能检查作者稿是否发布，而不是“保存窗口就悄悄改游戏”。

**事件时间有明确单位。** 教学示例：某轨道帧率120FPS，事件放在第48帧，导出触发时间为48/120=0.4秒。不能统一除以30或把120FPS动画当60FPS，否则声音和刀光时序都会偏。导出还核对原表对应动画、时长、表现身份和支持字段。

**身份不能靠文件名猜。** 同一技能可能有多个等级、职业、武器或表现段。工具通过绑定和既有表现行匹配，运行按选中的表现读取；不能因为文件叫Skill03就自行决定哪个角色使用它。

**特效位置也属于数据契约。** ActorRoot表示跟角色根；NamedSocket表示完整挂点路径；TargetTop表示目标模型顶部；CasterForwardWorld表示施法者前方的世界点；WorldAbsolute表示绝对世界位置。方向、偏移、缩放、是否跟随必须明确，否则在预览里看对、正式角色一转向就会偏。预览目标为空时的兜底不能证明真实目标顶部已验证。

**运行时一次登记，到期才执行。** `MArtSkill.FireEvents`按本次锁定配置登记计时器，`OnProcessTimer`接收一条到期指令，`InnerProcessTimer`分发到粒子/声音等操作。这里没有在每个Update把所有事件重复扫描一遍。若配置晚到，则按这次已经经过的时间登记原表现的事件，不重新选择别的段。

**模型冷加载为什么不能在开始时统一等全部资源？** 某条粒子到期需要角色Transform或武器挂点时，才向模型申请该条GO操作。模型已齐立即执行；模型未齐保存可取消票据，在基础GO初始化后交付。施法被打断/归池时撤销未交付操作，回调核对原施法和模型，避免旧动作晚到后出现在新角色上。声音需要Transform创建三维声源，也是本项目相对于RO音频接口的明确适配。

**编辑器预览与正式播放器保持不同职责。** 预览副本可以采样任意帧，反复重绘同一帧不能累积位移；正式角色仍通过现有技能/Animator/移动链执行。不能直接再挂Y的ActionPlayer让它与MAnimator争夺同一个模型。

**为什么不能只检查导出的粒子不为空？** 粒子引用在包中存在，但透明Shader对应变体缺失，画面仍可能白框。完整验收要看作者数据、Runtime字段、实际包依赖及真实渲染四层，详见难点三和问题十。

**可以直接讲给面试官**：

> 我们复用技能编辑器作为制作端，宿主负责把支持的轨道导出成运行表现。一个事件从帧转成秒后由技能计时器登记，到期才播放粒子或声音；模型没加载好就等待那一条GO操作，而不是重新跑整张时间线。正式角色只用一个技能动画入口。工具里可以看到很多轨道，但没有对应导出和运行处理器的内容会明确拒绝，避免制作成功、游戏实际忽略。

源码：`LYF_MMO/Assets/GM_Game/Editor/Skill/SkillEditorAssetTools.cs`、`LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Skill/SkillRuntimePresentation.cs`、`LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Skill/MArtSkill.cs`、`LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/3DModel/MModel.cs`。

### 四、A往前移动时，B为什么能看到A移动？

**本地先完成输入和碰撞。** A的输入转换成相机方向下的世界移动，自己的角色先在本地响应。项目用当前位置、朝向和移动状态与上次同步值比较，满足已有0.1秒节流等条件才上传。这是变化触发的上报，不是保证每秒固定发送10包。

**上报除了坐标还有耗时。** `CostTime`按秒累计，位置用世界米单位，朝向用角度。更新入口原来用整数毫秒，所以转换是乘0.001。教学示例：100毫秒应发0.1秒；若错发100，远端估计速度会差三个数量级。停止和只转向也要有正确状态语义，不能只上报“有输入”。

**服务器从会话找A，通知里补RoleId。** 当前11180经过网关和逻辑队列，`ROMoveComponent.OnMoveStart`更新在线角色基础Pos，再复用同图100米附近过滤发11181。服务端不让客户端请求任意给B改坐标；但当前终点来自A的客户端，完整速度/路径/服务器碰撞校验仍未完成。

**B保存影子目标，然后追赶。** B用RoleId查已有A实体，存新目标、朝向、移动状态与耗时，`LagSyncUpdate`估算速度并追赶。普通分支抵达后按移动标志保持/结束动画，不是无限按最后方向外推；当前没有抖动缓冲、RTT历史回滚等完整系统。

**技能位移有另一种生产者，但需要同一个消费入口。** 动画通过`SkillRootMotionCollector`提供有效窗口内的水平增量；程序位移提供额外增量。技能分支把它们合起来经过碰撞移动一次。普通影子追赶当前还有直接目标更新路径，不能把所有远端移动都说成已经统一服务器物理碰撞。

**教学示例：为什么不能盲目相加？** 同一帧动画想前进0.08米，程序想前进0.02米，共请求0.10米；墙挡住后实际只前进0.06米。同步残差应根据0.06米的实际落点重算，不能按理论0.10米认为已经到位。同帧再叠一份追赶会重复推动；所以存在技能位移的帧避免叠加普通追赶。

**可以直接讲给面试官**：

> 当前移动同步是A上报实际终点、服务器更新并转发给附近玩家、B追赶影子目标。技能根运动还必须在B端实际消费，不能只有动画。我们曾发现远端根位移采出来了但没有消费，技能期间普通追赶又被禁止，所以看起来播完才补移。补上消费后还要防止同帧双走，并按碰撞后的实际位置重算剩余距离。

### 五、TCP收到字节后，如何进入20Hz游戏逻辑？

**TCP提供字节流，接收回调不是一条消息。** 一条消息可能拆成两次接收，两条消息也可能一次全到。项目实际帧是两字节小端长度、1字节压缩标志、2字节CRC16及消息体，超过200字节的消息体按现有规则GZip压缩；长度表示后面的整段，不包含两字节长度头。

**教学示例：两个包混在一次接收中。** A帧体长度10字节、B帧体长度8字节，各自含标志/校验/消息体。先只收到A的1字节长度头时不能解析；再收到剩余长度头、A全部帧体与B的3字节，循环取出完整A，B的部分留在缓存开头；下一次B补齐后再解析。不是每次`EndReceive`都立刻Protobuf.Parse。

**为什么不在接收回调扣蓝？** 回调运行在网络线程，此时逻辑线程可能在检查角色状态。如果两边直接写同一角色，单个操作正确仍可能组合错。Game回调只投递命令，逻辑主循环从队列取出后才调用Handler和技能组件。ConcurrentQueue保证跨线程交付，不自动让字典和角色都变线程安全。

**两级队列意味着什么？** 总队列出队后将命令移交模块队列，再由模块查询来源与协议注册表执行一次。不是两级各执行一次TryCast，所以不能仅看有两个队列就认定重复扣费。

**20Hz怎么产生？** Stopwatch测真实经过时间，累加到毫秒；每积累50毫秒推进一个Tick和业务模块，每轮最多追赶5帧，余量不丢。网络阶段在每次主循环先执行，不一定仅每50毫秒处理一次。故服务端Tick频率、收包处理时机和客户端移动发包频率是三个概念。

**教学示例：一轮积累120毫秒。** 运行两次50毫秒逻辑更新，余20毫秒留下一轮；若积累400毫秒，本轮最多执行250毫秒，150毫秒留后续处理。服务器慢时仍可能产生积压，这个上限没有证明系统能承受多少在线玩家。

**真实问题为什么单测没抓住？** 之前技能测试直接推进Tick，技能能按期结束，但忙循环产生Tick的时钟转换丢亚毫秒。完整链路需要测试“时间如何被生产出来”，详见难点五。

**可以直接讲给面试官**：

> 网络层先把字节流拆成完整帧，再反序列化为业务包。收包线程只投递命令，角色状态由Game主循环集中修改。网络分发和固定逻辑步长分别处理，技能CD用Tick判到期。有次主循环不停跑但Tick几乎不变，原因就在整毫秒截断时丢掉未计入的余量，而不是技能结束方法本身有问题。

源码：`LYF_Server/Network/Socket/com/NetUtils.cs`、`LYF_Server/Network/Socket/com/ServerBase.cs`、`LYF_Server/GameServer/GameGlobal.cs`。

### 六、为什么编辑器修好了，安装包仍可能报同样的错？

**首先区分三种东西。** C#源码是正在编辑的内容；GM_Game.dll是编译结果；YooAsset包里TextAsset保存真正下载的DLL字节。Editor可能直接用当前编译程序集，安装包通过`Assembly.Load`用资源中的字节，二者不会因同一源码文件已保存就自动一致。

**启动按阶段走。** Boot初始化资源包，查询版本，获取对应清单，比较并下载差异，然后载入业务DLL与AOT补充元数据，成功后进入登录。显示“没有资源更新”仅说明下载器没有新文件，不能证明DLL已装载成功；发生异常时最后一条UI文字可能停在那里。

**如何确认不是凭感觉说“旧代码”？** 项目曾从995实际代码Bundle提取GM_Game DLL，比较字节哈希，并查看`OnUpdate`的方法IL，确认其中仍有空表时访问数组的指令。此时Editor方法已经恢复短路；所以需要更新的是热更编译与资源产物，而不是继续改同一段正确源码。

**为什么有些错误必须重建主包？** `MMoRpgCommon`当时属于主包AOT依赖，旧安装包根本没有该程序集/类型，新热更DLL却引用它。补充AOT元数据只为主包已有的AOT代码提供相关元数据，不能凭空把缺失的原生编译程序集补进旧GameAssembly。因此需要生成配套AOT/热更产物、资源版本以及完整主包。

**版本检查也要分步骤。** 版本查询失败却检查初始化成功状态，会把空版本继续交给清单操作。初始化成功不代表版本查询成功，工具打印compile finish不代表IL后处理成功。每一步的结论必须来自它自己的结果。

**可以直接讲给面试官**：

> 我遇到过两种“源码对、包里错”的情况。一种是热更包仍含旧DLL，通过实际字节与方法IL确认；另一种是新热更DLL依赖旧主包不存在的AOT类型，需要重新构建配套主包。排查顺序是先确定执行失败的阶段，再核对实际程序集和资源版本，不只是删缓存或一直重编。

依据：`项目分析/BUILD_LOGIN_STUCK_AOT_MISMATCH.md`、`项目分析/BOOT_HFS_VERSION_REQUEST.md`、`项目分析/SKILL_FX_PACKAGE_RUNTIME_DIAGNOSIS.md`。

## 技术难点案例：准备深入讲的内容

### 难点一：动画状态判断正确，为什么退出技能仍会下沉？

日期：2026-10-13。状态：源码修复、编译与原生隔离验证通过，修后正式双客户端全技能画面待验。

**背景与影响**：用户反馈本地与另一端观察角色放技能时瞬间下沉再恢复。此前已经修过快速停走时待机平移和远端根运动，需要保留这些修复。

**为什么难**：逻辑请求状态、Animator当前采样状态和过渡状态并不同时改变。技能逻辑结束不能证明旧动画已经停止参与混合；仅看角色坐标，也看不出骨骼姿态是否异常。

**排查与证据**：先分层采集Entity、模型根、Animator根与脚部高度。45秒纯待机样本没有施法，不能算复现；普通技能请求又被MP不足拦住。通过正常入口释放零费用F后，捕获实体Y始终18.73892，但退场时真实Slider_F被替成空Skill，左脚低于根约0.41695米，随后Idle接管恢复。完整真实动画固定根采样没有同样下沉，因此不能直接修改所有动画的高度。

**根因**：前轮为修快速停走，沿RO令 `MAnimator.InState` 比较最近播放请求。额外的资源释放方法仍依赖旧语义：刚请求Idle但Animator还没评估CrossFade时，原生仍在Skill且 `IsInTransition` 可能为false，真实剪辑被提前归还。

把故障按时间拆开，更容易解释：

| 时刻 | 代码认为要播放什么 | Animator实际还在使用什么 | 旧释放逻辑造成的结果 |
| --- | --- | --- | --- |
| 技能进行中 | Skill | 真实技能剪辑 | 姿态正常 |
| 动作窗结束，刚提交Idle请求 | Idle | 尚未评估新请求，仍采样Skill，过渡标记也可能还没变化 | 误认为技能已退出，归还真实剪辑并恢复空占位 |
| 接下来一次动画采样 | Idle | 旧技能槽仍可能参与姿态计算，但内容已变为空占位 | 脚部姿态异常，世界坐标却未下落 |
| Idle真正接管 | Idle | Idle | 姿态恢复，形成“下沉一下马上复原”的观感 |

这里需要分开回答两件事：“是否需要再次请求某个动画”看最新请求；“某个动画资源是否可以释放”看原生实际使用状态。它们不能共用同一个语义。

**方案与取舍**：只在 `TryReleasePendingSkillAnim` 读取原生当前状态，并保留已有过渡保护，等实际退出才释放。保留 `InState` 的请求去重语义。冻结骨盆、修改动画高度或撤销前轮停走修复，都无法正确处理这个生命周期问题。

**关键文件**：`LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/3DModel/AsyncObj/MAnimator.cs`。

**验证与边界**：开发与独立280源编译零错误；10项生产方法专项通过。真实Humanoid隔离测试明确构造“请求FIdle、原生仍Skill、未进入过渡”的缝隙，剪辑仍持有；随后12帧过渡保留，实际退出才释放，20帧最低脚高为根上方0.1100968米。此为PreviewScene隔离验证，尚未代表修后正式双端全技能或安装包结果。

**未解决事项与复盘**：正式双端画面需回归，包需要更新热更代码。接口语义调整后必须检查所有调用方，尤其资源释放不能拿“播放请求”代替“仍被使用”的事实。

**面试讲述**：项目中有一次技能退场瞬间下沉。排查时先区分世界坐标和骨骼姿态，发现根坐标没掉，真正变化的是技能剪辑在过渡中被释放。进一步定位到请求状态与原生采样状态存在一帧缝隙，最终只修资源释放判断，并用真实Animator重现这个时序验证。

**可能追问**：为什么只判断 `IsInTransition` 不够？为什么不能把 `InState` 全改回去？怎样证明是提前释放而不是根运动Y错误？答案分别对应评估缝隙、快速停走的请求去重语义、分层高度与真实clip采样证据。

详细分析：`项目分析/SKILL_EXIT_CLIP_RELEASE_HEIGHT_DIP.md`。修改记录：`项目修改日志/2026-10-13-SKILL-HEIGHT-DIP-CHANGELOG.md`。

### 难点二：远端能播技能，为什么根运动结束后才补移？

日期：2026-10-13。状态：源码、专项与原生隔离验证通过，正式双端修后施法待验。

**背景与影响**：A释放位移技能正常移动，B看到A原地播放，结束后才追赶位置。动画和同步包都存在，单看播放或收包不能定位问题。

**为什么难**：动画根运动、程序位移、网络影子位置和碰撞都可能写角色坐标。补上根位移后，如果仍叠加影子追赶，就可能双倍移动；若只扣理论距离，碰撞后又会留下错误残差。

**排查与证据**：沿实际消费者对照本地与远端更新。本地消费 `Model.RootMotion.ConsumeDelta()`，远端只处理普通追赶和程序位移。采集器本来允许远端采根，但远端缺少消费入口；技能禁止主动移动时，普通追赶又提前返回，积累的坐标差等技能结束才消化。

**根因**：远端技能根位移的消费链缺口，与普通移动追赶限制共同造成延迟补移。

例如一个带滑步的技能，动画每帧既改变手脚姿势，也产生一小段水平位移。A端把这段位移交给移动组件，所以边出招边前进；B端能收到技能开始并播放同一动作，却没有取出采集器里的位移。此时普通位置追赶又被技能的移动限制挡住，于是B端只有动作、没有平移。等技能结束，追赶恢复，才突然移动到服务器已通知的位置。这是症状的完整形成过程，不能只说“网络不同步”。

修复后的链路是“取根位移 → 与程序位移合并 → 碰撞移动一次 → 读取实际落点 → 重算到网络目标的剩余距离”。撞墙时真正走了多少，要以碰撞后的落点为准。上述统一碰撞针对技能位移分支；普通 `LagSyncUpdate` 仍有直接位置更新，不能扩大为全部远端移动都已统一物理权威。

**方案与取舍**：仅改远端 `MMoveComponent.Update(int)`，根位移与程序位移合并为一次碰撞移动。有实际技能位移的帧跳过普通追赶，按碰撞后的真实落点重算已有方向、距离和计时；精确抵达收束移动态。保留协议和服务器，避免为已有客户端消费缺口增加新同步消息。

**关键文件**：`LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Component/MMoveComponent.cs`。

**验证与边界**：独立修前15项复现/回归、修后19项通过，280源编译零错误。原生隔离正式远端Prefab、Humanoid、Collector和CharacterController，40帧根累计4.999855米、实际4.999854米，结束额外位移0、移动态false。Edit测试显式调用根采样回调，首次夹具未采根和Rebind起点不一致均修临时装配，不能据夹具失败改生产代码，也不能把隔离数据称正式联机结果。

**未解决事项与复盘**：正式双端及包需回归。排查同步要把生产、消费、实际碰撞提交、残差更新串成完整链，不能仅以“收到坐标”判断同步正常。

**面试讲述**：项目中曾出现远端技能播完才补移。沿根运动链检查后发现采集存在但远端没有消费，同时普通追赶被技能状态限制。修复时统一一次碰撞提交，并按实际落点重算同步残差，隔离验证约5米位移后没有尾部补移。

**可能追问**：为什么不直接给远端叠加deltaPosition？碰撞后应该扣理论距离还是实际距离？如何避免技能结束重复追赶？核心是单次坐标提交、实际落点和残差一致性。

详细分析：`项目分析/SKILL_ROOT_MOTION_SYNC.md`。修改记录：`项目修改日志/2026-10-13-SKILL-ROOT-SYNC-CHANGELOG.md`。

### 难点三：特效资源都能加载，为什么包内颜色和形状仍不对？

日期：2026-10-13。状态：两个目标特效在临时真实资源包中的修复与视觉对比通过，正式客户端现场仍待验证。

**背景与影响**：Skill3出现白色矩形、Skill04出现黑色粗轮廓，用户怀疑shared漏包。材质、贴图和Shader引用都非空，仍不能说明实际渲染正确。

**为什么难**：相同Shader名称、材质参数与 `isSupported` 标记，无法证明包内包含实际使用的关键词变体。粒子随机性和测试依赖加载错误又可能干扰源/包对比。

**排查与证据**：固定相机、粒子种子和时间对比源/包画面；有效材质字段一致，43对贴图RGBA逐像素一致。仅在包克隆中将目标Shader替成源Shader后异常显著消失，将主要差异定位到Shader执行。随后发现收集器保存到Assets根目录，而正式打包收集GM_Game/Shaders旧集合：新集合77 Shader/165变体，1071真实包仍17/20。

**根因**：变体收集输出路径与正式资源收集路径不一致，新收集结果没有进入实际Shader包。该批共享材质与贴图未发现漏入包证据。

可以这样解释“资源没丢，画面为什么还错”：材质保存颜色、贴图和关键词，Shader负责决定这些数据怎样画到屏幕。同一个Shader可以按透明、发光、噪声等关键词编译出不同版本；包里能找到Shader对象，只说明存在这个资源，不能说明实际材质需要的组合也被保留。本项目是新变体集合保存到了一个位置，而打包仍读取另一个位置的旧集合，所以继续重复打包也会重复使用旧输入。

实验必须控制粒子随机性：同一相机、同一随机种子、同一播放时刻，比对源资源和实际包实例；再只替换Shader观察异常是否消失。否则两次粒子散开位置不同，也会被误当成打包导致形状变化。这里记录的是实际做过的控制实验，并非据报错猜测shared有问题。

**方案与取舍**：将保存路径对齐原正式目录，同步正式collection及JSON，保原GUID和用户根资产；不扩大整个资源收集目录、不关闭shared或给全库Shader强制保留所有变体。

**关键文件**：`LYF_MMO/Assets/GM_Game/Shaders/ShaderVariantCollectorSetting.asset` 的SavePath，以及同目录 `MyShaderVariants.shadervariants`、`MyShaderVariants.json`。

**验证与边界**：临时真实43包原生读取77/165；两个目标共8个采样对与源逐像素相同，白框与黑轮廓消失。六特效24对仅19对完全一致，其余5对轻微差异仍保留。最初测试误用模拟清单加载实际依赖，导致Particle为空，之后仅修临时夹具使用真实AssetBundleManifest。构建中另有Shader Compiler IPC错误，不能用两目标画面通过宣称全构建零错误。

**未解决事项与复盘**：正式版本和主城画面仍需按原流程验证，编译IPC故障另行分析。资源验收要分别证明收集、入包、依赖加载和实际渲染，存在引用只是其中一步。

**面试讲述**：曾排查技能特效在包内变成白框或黑轮廓。先验证材质属性和纹理像素，再做Shader替换控制实验，最终发现变体集合保存目录与正式收集目录错位。修复路径后用真实包计数和固定粒子渲染对比验证，没有通过修改材质颜色掩盖问题。

**可能追问**：Shader引用不空为什么还会渲染错？如何排除粒子随机性？为什么模拟清单不能代表实际包依赖？分别对应关键词变体、固定种子/时间与重复控制、实际Manifest闭包。

详细分析：`项目分析/SKILL_FX_APPEARANCE_SHADER_VARIANTS.md`。修改记录：`项目修改日志/2026-10-13-SKILL-FX-APPEARANCE-CHANGELOG.md`。

### 难点四：动作结束了，为什么技能实例还不能立即回池？

日期：2026-10-13整理。状态：当前源码已实现职责拆分，历史代码级专项已验证；本轮仅总结，不新增运行验收。

**背景与影响**：连续普攻接段时，新技能需要接管动作槽，但旧刀光、延迟粒子和声音可能仍在运行。模型或表现资源还可能晚于计时器加载完成；复用同一池对象后，旧异步回调不能继续操作新施法。

**为什么难**：这里至少存在四种寿命：当前动作占槽、服务器施法状态、客户端表现尾段、资源引用。把它们全部绑定到动画长度，会截断尾声或提前释放；把所有内容都留着，又会让旧技能占状态或继续产生位移。

**排查与依据**：当前`MSkill`分别提供`HasServerEnded`、`IsAnimationFinished`、`IsPresentationFinished`与`Cease`。`MArtSkill.Start → FireEvents`注册时间线，`MTimerMgr → OnProcessTimer → InnerProcessTimer`处理单条到期事件；真正用到模型GO时才登记`AddLoadGoCallback`，不在技能Update重复扫描整张时间线。对象复用使用已有UUID与施法代次区分旧操作。

**根因与关键矛盾**：动作结束只代表不再拥有当前动画/位移，不能代表所有表现完成；UUID识别一次施法，池对象引用本身不能证明仍属于原来的那次使用。资源共享和旧技能持有核心，也不能在替换字典项时直接释放。

**方案与取舍**：当前动作和旧施法列表分别持有实例；自然结束释放动作/根归属，允许未来事件与完整声尾收尾，真正打断注销等待并停止对应表现，最后由终止入口清理回池。技能核心由字典与仍存活的施法持有，最后一个持有者解除后才归还；粒子保持自己的资源租约。沿RO事件与模型回调职责适配，避免为了方便把所有逻辑塞进Update或统一延长动画占槽时间。

尾段完成后的本地回池沿当前存活判定执行，不额外要求等待服务器End确认；服务器状态和迟到回包仍按原身份处理。正常回池也不清除合法CD，冷却记录与表现实例回收独立。

**关键文件**：

- `LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Skill/MSkill.cs`
- `LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Skill/MArtSkill.cs`
- `LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Component/Action/MSkillComponent.cs`
- `LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/3DModel/MModel.cs`

**验证与边界**：既有专题记录覆盖自然结束保尾、打断清理、冷模型、旧回调、对象归池与重新使用等代码级回归。当前源确认入口职责仍存在；本轮没有重新执行那些历史测试。正式场景听感、网络迟到与全部组合仍按原验收记录说明，不能说仅靠对象池就已证明零GC或零泄漏。

**复盘**：对象池首先是所有权和生命周期问题，其次才是分配优化。需要回答谁借出、谁持有、谁解除、异步回调何时失效，不能仅展示一个空闲栈。

**面试讲述**：技能接段时，动作退出和表现结束不是同一个时刻。项目把当前动作与旧施法分开，动作退出只交还动画和位移，尾部粒子与声音完成后再回池；异步操作还需要检查它是否属于这一次施法，避免旧回调污染复用对象。

**可能追问**：为什么UUID之外还要施法代次？技能升级后旧核心何时释放？自然结束与打断如何不同？答案分别是池对象可能被重新使用、旧施法还持有原核心、自然结束允许尾段而真实打断立即取消。

### 难点五：主循环一直在运行，逻辑时间为什么几乎不前进？

日期：2026-10-12故障，2026-10-13整理。状态：最小修复与真实Update隔离对比通过，后续正式进程只读采样确认20Hz正常推进。

**背景与影响**：第一次F已被接受，随后反复提示状态不允许施法。活动技能和CD长期不结束，看起来像技能状态机没有清理。

**为什么难**：网络请求确实到达，施法代码也正确；在测试里手动推进Tick可以自然结束，所以只测技能组件会漏掉真正产生Tick的主循环。

**排查与证据**：只读进程确认技能结束Tick为22，但间隔16秒两次采样LogicTick仍为10。沿`GameGlobal.Update`发现，每轮把Stopwatch刻度差截成整毫秒，再把采样原点无条件重置为当前时刻。忙循环多数间隔不足1毫秒，得到0后丢掉余量，50毫秒固定帧一直攒不起来。

**根因**：时间源正常，但整数单位转换与原点更新组合造成未计入时间被反复舍弃。

**方案与取舍**：只按已经计入的完整毫秒推进采样原点，不足毫秒的刻度留到下一轮。原50毫秒步长、每轮最多5帧追赶和剩余时间保留机制保持。没有通过放开状态限制、强行结束技能或另建时钟来掩盖故障。

**关键文件**：`LYF_Server/GameServer/GameGlobal.cs`，`Update/GetElapsedMilliseconds`。

**验证与边界**：隔离进程连续调用真实Update，修前1200毫秒仅1Tick，修后25Tick，滑步动作和CD自然到期，第二次F成功；原专题7项断言通过。后续正式服务只读样本LogicTick92020→97767，约287秒推进5747帧，符合20Hz。当前MP耗尽的不能施法是另一个原因，不能把旧时钟结论套到每次拒绝。

**复盘**：固定步长不仅要在累积器中保留不足一帧的时间，也要在时钟单位转换时保留尚未计入的精度；测试需覆盖真实时间生产入口。

**面试讲述**：曾遇到服务器循环正常、技能却不结束。读取进程发现逻辑Tick不变，最终定位到高速轮询时整毫秒截断后重置原点，亚毫秒时间一直被丢弃。只修原点推进方式，保留余量，再用真实Update高速循环验证计时恢复。

**可能追问**：为什么用Stopwatch？为什么单测技能通过仍出问题？最大追赶次数是为了什么？分别对应单调时钟、测试没有覆盖时间来源、防止单轮长时间追赶挤占其他处理；上限不意味着丢掉剩余时间。

来源：`项目分析/SERVER_LOGIC_CLOCK_MS_REMAINDER.md`。修改记录：`项目修改日志/2026-10-12-ROLL-STATEBLOCKED-FIX-CHANGELOG.md`。后续现场：`项目分析/SKILL_STUCK_SERVER_MP_DIAGNOSIS.md`。

### 难点六：两个账号同图且距离很近，为什么互相看不见？

日期：2026-10-13。状态：最小修改、编译和回环/原生隔离验收通过；正式重登画面以实际运行记录为准，不扩大为完整动态AOI验收。

**方案与取舍**：在本地模型和出生点绑定完成后，先通过既有11180上报初始坐标，再发11070入场。远端初始坐标读取服务器已有Pos，并给旧兼容控制器绑定同一实体，避免旧重力/根运动重复写坐标。不扩大附近范围、不让移动包兼做创建、不引入额外等待确认或重试。

**关键文件**：`LYF_MMO/Assets/GM_Game/Scripts/Manger/MainCityMgr.cs`。

**验证与边界**：真实队列/回环TCP修前8项复现、修后19项双向入场/移动通过；正式服务程序集副本隔离13项通过。原生Prefab验证旧控制器绑定后不再额外写坐标，末稿位置/绑定抽取段4项通过。这些证明对应时序和写入问题修复，不能替代正式客户端完整异步登录流程或离开视野/重新进入的动态AOI能力。

**面试讲述**：双账号互不可见时，排查没有停在“服务器当前距离没问题”，而是回看第一次入场计算使用的位置。初始位置尚未上传导致附近通知被过滤，而移动消息不会补建实体。最终调整已有上报与入场顺序，使空间状态先就绪再触发视野初始化。

### 问题七：为什么随便按移动键，也会概率待机平移？

日期：2026-10-13。状态：公共动画链两处修复、编译与代码专项通过，正式双端反复停走画面待验。

**现象与难点**：A的坐标持续向前，模型却保持待机，B看A也一样。输入和位移没有完全失效，而且不是每次发生，需要查两端共用的默认动作链。另一种现场还出现逻辑要求FIdle、原生长期仍播放Skill04，不能把两种动画不一致混为同一个原因。

**第一处故障按时间说明**：正在Walk时松开键，提交0.1秒过渡到Idle；过渡未结束又按方向键，移动组件再次要求Walk。旧 `InState(Walk)` 读到过渡源仍为Walk，便跳过新请求，但Animator正在执行的目标其实是Idle。旧过渡继续完成，动画刷新标记又已清零，于是位置继续走、姿态停在Idle。本地和远端使用同一判断，因此都能出现。

**第二处证据与根因**：默认动作 `PlayAnim` 从RO保留了后摇时间计算，时间大于零就返回，但对应 `SetTimer` 和回调没有移植，`killTimer` 也是空体。代码说“以后恢复默认动作”，实际上没有人负责以后调用，造成技能后默认动画假恢复。

**最小修改与取舍**：RO的 `InState` 比较最近请求；本项目已有 `_currentState`，直接使用，不新增状态字段。默认动作删掉没有实际调度的延期分支，动作窗结束沿现有入口播放默认动作。保留跳跃/落地保护和走跑规则，不通过每帧强制重播解决问题。随后出现的退出下沉，是资源释放调用方漏适配新语义，见难点一；请求去重和资源释放分别判断。

**关键文件与验证**：`LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/3DModel/AsyncObj/MAnimator.cs`、`LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Component/Action/MDefaultActionComponent.cs`。280源编译零错误，生产方法抽取专项30项前后对照通过，涵盖本地/远端走跑、快速恢复和技能回默认。原生探针受临时装配和用户构建占用影响，未取得完整成功结果；不能讲成真人双端画面已全部验收。

**面试口述**：“这里移动不是没执行，而是动画切换被去重判断挡住了。停止时已请求Idle，但再次按键时旧Walk还参与混合，代码就误以为不用请求Walk。把判断改为最近请求后，恢复移动会覆盖旧Idle目标。另一个技能后不恢复的问题，是移植了延期返回却漏掉定时回调，按当前动作窗流程删掉失效延期即可。”

**追问与遗留**：为什么不每帧Play？会不断重置播放，不解决语义。为什么本地与远端同现象？共用默认动作链。后续需对应版本正式双端停走、施法后移动回归。来源：`项目分析/MOVE_IDLE_SLIDE_ANIMATION.md`、`项目修改日志/2026-10-13-MOVE-IDLE-SLIDE-CHANGELOG.md`。

### 问题八：为什么表里有CD，技能却能无限释放？

日期：2026-10-11。状态：最小双源修复、真实输入链隔离前后对照通过，正式网络/Unity场景待验。

**现象与排查顺序**：先确认配置不是零CD，再确认毫秒转秒和输入准入查询，最后观察CD在哪个时刻变成0。历史核实五个技能10010/10040/10050/10060/10070为0.5/8/10/9/13秒，冷却组全0。短CD可能在长动作结束前正常到期，但不能解释十秒CD半秒后消失。

**决定性证据**：隔离真实 `SkillCtrl` 与请求链，设置十秒CD、半秒表现且不回包。修前0.61秒表现实例正常回池，CD变0，第二次输入又成功。这把问题定位在本地收尾，而不是服务器回包覆盖或配置读取失败。

**根因与方案**：`MSkill.Cease` 的预表现分支调用 `Core.Reload`，把正常提前结束的表现当成应该清冷却的清理。删除这一调用和已无其它调用的Reload方法。冷却属于已学技能核心及冷却记录；池化对象属于这次动画/特效，两种寿命独立。正常回收只释放该次表现，不新增确认锁、不要求等回包再回池。

**关键文件与结果**：`LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Skill/MSkill.cs`、`LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Skill/MSkillCore.cs`。同条件修后0.61秒仍余9.39秒，连续20次按键没有发包或创建新实例，十秒到期后允许再次输入。归档总验收298项含受影响回归、输入专项和配置专项，272源零错误；这是历史隔离数据，本轮未重跑。

### 问题九：为什么移动报空引用，编辑器修完安装包仍旧报错？

日期：2026-10-13。状态：源码短路修复及专项通过，995旧代码包已实证；该版本更新后的Player移动验收未完成。

**现象与证据**：编辑器移动时 `MDefaultActionComponent.OnUpdate` 原第296行空引用。脚步时间表 `_footStepsTimes` 未配置为null是正常情况，原条件应在表存在、下标有效后才读取数组。这里不是必须给所有角色新增脚步表。

**根因具体是什么**：拆分长布尔表达式时，先把包含数组读取的后半条件算成局部变量，再与前半条件组合。原来 `A && B` 在A为假时不执行B；提前计算B后，即使A为假，也已经访问空数组。教学示意：‘先判断表存在，再读某项’变成‘先读某项，再判断表存在’，最终真假值看似相同，但执行过程不等价。

**最小修复**：保留原业务条件和短路次序，先进入表存在及下标有效的分支，再读取时间。满足每表达式最多三项的约束，无新增配置或多层异常包装。对应 `LYF_MMO/Assets/GM_Game/Scripts/SceneEntity/Component/Action/MDefaultActionComponent.cs`。归档18项生产方法与4项原生Animator专项通过，280源零错误。

**为什么包仍报错**：995真实代码Bundle提取的GM_Game.dll为567808字节，SHA与正式Dlls目录当时的旧字节相同。检查 `OnUpdate` IL仍存在空表后执行 `ldelem.r4` 的路径；编辑器新IL则已恢复短路。Boot编辑器分支不反射加载该包DLL，Player却使用包中字节，所以同一源码目录能对应两种运行结果。

**面试口述**：“这次排查分两层。源故障是拆条件时丢了短路，让移动访问空脚步表；修复后编辑器正常，但包仍报同错。我进一步提取实际Bundle里的DLL看方法IL，确认Player还在用旧实现。源码修改、热更编译、资源更新和运行版本必须逐层对齐，不能靠编辑器编译成功判断包已修好。”

**追问与遗留**：为什么比较IL而不只看时间戳？直接确认故障方法是否进入产物。旧包需按原流程重新生成热更DLL和资源并验证，归档时未替换或发布。来源：`项目分析/DEFAULT_ACTION_SHORT_CIRCUIT_RUNTIME_FIX.md`、`项目分析/SKILL_FX_PACKAGE_RUNTIME_DIAGNOSIS.md`、`项目修改日志/2026-10-13-SKILL-FX-RUNTIME-ACCEPTANCE-CHANGELOG.md`。

**另一个误导点**：HybridCLR `CompileDllCommand` 当时不检查ScriptCompilationResult就打印finish，项目BuildDll随后仍复制已有DLL。菜单跑到结尾和出现文件可能只证明旧文件被复制，不能证明本次编译成功。这轮没有顺带改第三方工具源码。

**排查操作与取舍**：保存原响应参数、日志及正式输入哈希，用相同123个define、243个reference、同程序集和Runner，只把输出改到_temp，单次Jobs/Burst后处理完成且退出0。再请求正常脚本编译，真实 `CompilePlayerScripts` 返回typeDB为真和26个程序集。未删Library、替换依赖版本或主动发布DLL。

**面试口述**：“构建排查不能只看工具说finish。我先查原生后处理退出码，确认真正失败在ILPP，然后保留相同输入单独执行，验证生产源不是稳定复现的编译错误。恢复正常编译后，再看真实Player脚本结果。内部首次失败没复现，所以没有把缓存或Burst版本猜成根因，也没有把脚本编译成功扩大成完整安装包成功。”

**追问与遗留**：如何防止把旧产物当新结果？核本次返回值、完整错误日志、实际产物内容与运行版本；问题九展示了旧DLL的具体后果。此轮新增仅诊断证据与协作记录，关键链为HybridCLR编译菜单和项目BuildDll入口，未改业务源。来源：`项目修改日志/2026-10-13-BURST-JOBS-ILPP-CHANGELOG.md`。

### 高频追问与回答要点

| 追问 | 可以直接回答的要点 |
| --- | --- |
| 这个项目到底是状态同步还是帧同步？ | 当前玩家移动是位置状态上报与远端影子追赶；服务端20Hz指业务固定更新步长，不能因此称客户端确定性锁步。 |
| 客户端发送成功就代表技能成功吗？ | 不代表。发送完成后开始预表现，服务器仍可能因学习、状态、MP或CD拒绝，最终使用权威结果校正。 |
| 为什么要分MSkillCore和MSkill？ | 前者对应已学等级与技能配置，后者对应某次UUID的施法、时钟及异步生命周期；旧施法可能晚于核心替换才结束。 |
| 单次技能ID和施法UUID有什么区别？ | SkillId识别哪种技能；UUID关联这一次请求、预表现、广播和回包。UUID也不能直接当永久全局唯一ID或完整历史防重缓存。 |
| 为什么不能动画播完就释放一切？ | 动作结束后可能还有服务器状态、未来制作事件和音尾；动画clip还可能参与退出混合，需要分别判断。 |
| 编辑器里有轨道为什么游戏不能直接用？ | 制作数据、导出支持、运行处理器和权威规则必须逐项对应；窗口存在不等于正式执行链存在。 |
| 哪里真正体现了性能优化？ | 已有池化复用和一次位移提交，也关闭了主城54个实时点光；没有统一设备下的前后Profiler数据，不能报FPS提升或零GC。 |
| 服务器现在能防客户端改坐标吗？ | 当前主要接收客户端碰撞后的终点并广播，完整速度/路径/物理权威未实现；技能MP/CD权威与移动物理权威要分别说明。 |
| 如何证明热更客户端加载的是新代码？ | 比对实际资源版本、包中DLL字节和方法IL，随后验证运行行为；Editor重编及工具打印finish都不能独立证明发布成功。 |
| 第三方组件用了很多，自己做了什么？ | 按实际参与说明宿主绑定、导出契约、技能生命周期、移动接线和问题排查；Y编辑界面、YooAsset、HybridCLR和RO参考代码明确来源。 |
