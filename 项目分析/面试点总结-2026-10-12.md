## 0. 项目一句话介绍（开场用）



* 一个 Unity 2023.2 + C# 的 3D MMORPG，客户端用 **YooAsset + HybridCLR** 做资源与代码热更，服务端是 .NET Framework 4.8 的**分布式四服架构**（Login / Gate / Game / Center），通信走 **TCP + 自定义长度帧 + Protobuf**，配置用 **Luban**（Excel→bytes，前后端同源），持久化用 **MySQL(SqlSugar) + Redis**。

* 我主要负责 / 熟悉：战斗技能系统（客户端预测 + 服务器权威）、技能编辑器（Timeline 自定义轨道）、网络层拆包与分发、GameServer 线程模型与固定帧主循环、实体组件架构与移动同步。

* 项目亮点关键词：**参考 RO（仙境传说服务端）架构做的忠实移植**、网络线程与逻辑线程分离、技能对象池 + 施法 UUID 预测校正、动画根运动与程序位移合并、固定 20Hz 逻辑帧。

## 1. 网络层（客户端 + 服务端通用，高频）

### 1.1 TCP 粘包 / 半包处理 ⭐⭐⭐

**项目实现**（`Network/Socket/com/ServerBase.cs`）：



* 自定义帧格式：**2 字节&#x20;**`ushort`**&#x20;长度头 + Protobuf 包体**，`BasePackage` 内含 ProtoCode、Data (ByteString)、UnitySessionId/GateSessionId。

* 维护一块固定累积缓存 `_buffer`，大小 = 2 + 65535（`MaxFrameLength = ushort.MaxValue`）。

* `BeginReceive` 用 **APM 异步**（`BeginReceive/EndReceive`），把数据追加到 `_receiveLength` 之后。

* `ProcessReceiveBuffer` 循环拆帧：


  * 剩余字节不足 2 字节帧头 → break 等下次；

  * 读出长度 N，剩余不足 `2+N` → 半包，break 保留；

  * 完整则解析、分发，`parseOffset += 2+N`；

  * 循环结束把剩余半包 `Buffer.BlockCopy` 移到缓存头部。

* 长度合法性校验：`messageLength < 3` 直接抛异常断开；可用空间 ≤0 断开（防止恶意超长包撑爆内存）。

**追问与答题要点**：



* **为什么 TCP 会粘包？** TCP 是面向字节流的，没有消息边界，Nagle 算法合并小包、MTU/MSS 分片、接收方读取不及时都会导致一次收到多个包或半个包。UDP 面向报文则不会。

* **常见拆包方案**：①固定长度（浪费）；②固定分隔符（要转义，慢）；③**长度头 + 包体（本项目）**；④成熟的如 LengthFieldBasedFrameDecoder。

* **为什么长度头用 2 字节？** 单帧最大 65535，够放 Protobuf 消息；超过要分包。可追问：超大包（如批量背包）怎么办 → 业务分包 / 压缩 / 流式。

* **为什么用累积缓存而不是每次 new？** 减少 GC；本项目是 .NET  Framework 服务端，更要控制分配。

* `SendData`**&#x20;是同步阻塞发送的，有什么问题？** 高并发下 `Socket.Send` 可能阻塞网络线程；生产可改发送队列 + IOCP/SendAsync 双缓冲。这是本项目可主动承认的优化点（体现深度）。

* **字节序**：`BitConverter.ToUInt16` 依赖主机字节序（x86 小端），跨语言 / 大端平台要约定网络字节序（大端）或手动拼字节。

### 1.2 异步 Socket 模型 ⭐⭐



* `NetServer`：`BeginAccept` 异步接受连接，回调里 `EndAccept` 拿到客户端 Socket，创建 `Session` 后**再次调用 BeginAccept** 形成接受循环；`Listen(backlog=100)`。

* 每个连接一个 `Session`（继承 `ServerBase`），`SessionMgr` 统一管理，断开回调通知宿主。

* **追问**：APM（Begin/End）、EAP（事件）、SAEA（SocketAsyncEventArgs/IOCP）区别？高并发游戏服为什么常用 IOCP/SAEA 或封装好的库 —— 避免每次异步操作分配 IAsyncResult。本项目用 APM 是教学 / 中小规模实现。

### 1.3 协议序列化 ⭐⭐



* 用 **Google.Protobuf**，外层信封 `BasePackage`（协议号 ProtoCode + ByteString 载荷 + 会话字段），内层按协议号反序列化为具体消息（如 `SkillCastStartNtf`）。

* 协议号集中在 `NetDefine.CMD_xxx`；`.proto` 在 `ProtoBuf/proto`，生成代码放 Network。

* **追问 Protobuf 为什么快 / 小**：TLV 变体编码（varint 小数字只占 1 字节）、字段编号而非字段名、只序列化非默认值、二进制无可读文本开销。

* **追问协议号设计**：本项目一个协议号一个 Handler，按 `(来源, 协议号)` 注册；Gate 与 Center 来的相同命令号语义不同会拆不同 Handler。

* **版本兼容**：Protobuf 靠字段编号增删兼容（新增字段用新编号、不能改已有编号类型、reserved 保留废弃编号）。

### 1.4 客户端网络：主线程投递与连接代次 ⭐⭐

**项目实现**（`Manger/NetSocketMgr.cs`）：



* Socket 回调在**后台线程**，Unity API 只能主线程用，所以 `PostToMainThread(Action)` 把消息处理 marshal 回 Unity 主线程（用一个并发队列，Update 里消费）。

* `CurrentConnectionGeneration`（连接代次）：每次（重）连接递增；旧连接的迟到回调带旧 generation，比对不一致直接丢弃，**防止断线重连后旧 socket 的回调污染新会话 / 旧场景实体**。重连失败时按代次清理 SceneWorld。

**追问**：



* 为什么 Unity 只能在主线程调 API？Unity 引擎不是线程安全的，GameObject/Component/Transform 都绑定主线程；子线程只能做纯数据计算。

* 连接代次本质是什么？是一个**乐观的会话隔离令牌（epoch/generation token）**，和技能系统的 "施法代次" 是同一套思想，可类比讲解。

## 2. GameServer 线程模型与固定帧（服务端最核心，必考）⭐⭐⭐

### 2.1 网络线程 / 逻辑线程分离

**项目实现**：



* 网络线程（Socket 回调）**绝不允许直接改游戏状态**，只做一件事：把收到的 `BasePackage` 复制成一个**不可变信封&#x20;**`GameCommand` 丢进并发队列。

* `GameCommand`（`manger/Command/GameCommand.cs`）是 `sealed` 不可变类，字段只读：协议号、来源枚举、会话（UnitySessionId/GateSessionId）、`ByteString Payload`**（不可变副本，避免跨线程持有可变网络包）**、入队 UTC 时间、`Interlocked` 生成的全局递增序号、发送端 Transport。

* 总队列 `GameCommandDispatcher` 用 `ConcurrentQueue<GameCommand>`：


  * 入队用 `Interlocked.Increment` 先增计数做**容量闸门**（总积压上限 `MaxPendingCommands=20000`，超了拒绝入队并回滚计数，防内存无限增长）；

  * 出队每轮上限 `MaxCommandsPerTick=3000`，防突发流量挤占逻辑帧；

  * `volatile bool _accepting` 停服时先停止生产，再排空队列。

* 主循环 `GameGlobal.Update()` 运行在逻辑主线程：先 `DispatchPending()` 把总队列命令投到 `ClientMessageManager`，再驱动固定帧。

**为什么这么设计（必背）**：



1. **线程安全**：游戏状态（角色、背包、场景）只在一个线程改，天然无锁，避免给每个容器加锁的复杂度和死锁风险。这是主流游戏服（如本项目参考的 RO C++ 服务端、Skynet  actor 模型）的通用做法。

2. **可复现 / 确定性**：所有输入先排队按序处理，配合固定帧，逻辑执行顺序确定。

3. **背压保护**：队列上限 + 单轮消费上限，防止客户端刷包把服务器拖垮。

4. **不可变 + 数据拷贝**：跨线程传递必须不可变或拷贝，`ByteString` 本身不可变，杜绝网络线程复用缓冲导致的脏读。

**追问**：



* ConcurrentQueue 原理？无锁（Interlocked + 自旋），分段 / 链表 CAS 入队出队；本项目还额外维护 `_pendingCount` 是因为 `ConcurrentQueue.Count` 是 O (n) 慢操作，不能高频调用。

* 为什么不用 `Action` 闭包当队列元素？闭包会捕获可变网络对象、分配大、难审计、无法记录来源 / 序号；所以用强类型不可变信封（这也是项目明确的决策）。

* 网络线程和逻辑线程之间还有哪些跨线程数据？网关断开事件也走单独 `ConcurrentQueue<int>` 延迟到逻辑线程处理下线保存，不能在 socket 线程直接删角色。

### 2.2 固定步长主循环（20Hz）⭐⭐⭐

**项目实现**（`GameGlobal.cs`）：



* 逻辑帧间隔 `LogicFrameMilliseconds = 50`（**20Hz**）；用 `Stopwatch.GetTimestamp()` 取**单调时钟**（不受系统校时 / 手动改时间影响）。

* 每轮把真实流逝时间累加进 `_deltaMilliseconds`，`while` 累积够 50ms 就执行一个固定帧，`LogicTick++`，最多追赶 `MaxCatchUpFrameCount=5` 帧，避免卡顿后一次性追太多造成 "螺旋死亡"。

* 每个固定帧：先 `CTimerMgr.Update(50)`（服务器定时器），再按**固定注册顺序**调用各管理器 `Update(delta)`：Redis → RoGames → Role → Decouple → MonsterWave → … → Scene → WorldEvent → GVG。

* 每个管理器用 `try/catch` 包裹，**单个管理器异常只记日志，不中断其他管理器和主循环**。

* Buff、冷却、战斗、定时逻辑一律以 `LogicTick` / 服务器时间为准，不用客户端时间。

**追问（游戏循环经典三连）**：



* **为什么用固定步长而不是每帧渲染时间 dt？** 服务端要确定性和稳定结算；固定步长让不同机器、不同负载下逻辑一致，便于客户端预测 / 回滚与对账。客户端渲染则常用 "固定逻辑步长 + 可变渲染插值"。

* **什么是螺旋死亡（spiral of death）？** 一帧算不过来 → 积压更多帧 → 追赶帧又超时 → 永远追不上。本项目用 "最多追赶 5 帧 + 丢弃多余累积" 兜底。

* **Stopwatch 和 DateTime.UtcNow 区别？** DateTime 受系统时间回拨 / NTP 校时影响，会出现负 delta；Stopwatch 基于高精度单调计时器（QueryPerformanceCounter），适合算时间间隔。

* **为什么 20Hz？** MMORPG 对实时性要求低于 FPS/MOBA，20Hz（50ms）服务器结算 + 客户端本地预测 / 插值足够，且省带宽和 CPU。FPS 常 20\~60Hz，帧同步游戏常固定逻辑 15/30/60Hz 且锁步。

* 管理器更新顺序为什么重要？有依赖关系（如先 Redis 拉数据再 Role 逻辑）；顺序在 `GameModuleManager` 预注册，是启动配置而非动态排序。

### 2.3 协议分发与处理器注册表 ⭐⭐



* `ClientMessageManager` 是入站队列消费者 + Handler 注册表，网络回调只入队，Handler 只在逻辑线程跑。

* 每个 `(GameCommandSource, CommandCode)` 注册一个同名 Handler，按领域分目录（Login/Role/Knapsack…），`GameMessageProtocolRegister` 统一登记（对应 RO 的 `CProtocolRegister::Register`）。

* Center 回包分两类路由：`ForwardToGate`（必须**先原样转发给 Gate 再执行本地 Handler**，如给客户端的回包）与 `Internal`（只 GameServer 消费，如持久化确认，禁止因带会话字段就转发）。

* Gate 是面向客户端的错误码边界：失败先回权威数据再发 `CMD_ErrCode` 触发 Tips，避免重复弹窗。

## 3. 战斗技能系统（客户端最核心，本项目最大亮点）⭐⭐⭐

### 3.1 整体职责链



```
玩家按键
  → MSkillComponent.CanStart 统一门禁（CD/MP/跳跃 IsJump/技能规则 SkillCastingRules）
  → 通过：客户端立即预测（播动画/特效/本地进CD）+ 同时发请求给服务器
  → MSkillFactory 从对象池借 MSkill(MArtSkill) 实例 + MSkillCore
  → MArtSkill.Start → FireEvents()：把特效/音效/位移事件一次性注册到 MTimerMgr
  → MTimerMgr(整数毫秒时钟) 到期 → OnProcessTimer → InnerProcessTimer 执行 fx/audio/charge
  → 动画根运动：SkillRootMotionCollector 采 Animator.deltaPosition(XZ)
  → MMoveComponent 合并：输入 + 重力 + 动画根 + 程序位移 → 一次 MoveCharacter(碰撞)
  → 服务器权威回包(按 skill_uuid/attackSeq 配对) → 校正 CD/MP，广播给附近玩家
  → 自然 End：保留未来计时器/GO请求/完整声尾，全收尾后 Cease 回池
     Interrupted(打断/拒绝)：立即注销票据、停声、回池
```

### 3.2 客户端预测 + 服务器权威 ⭐⭐⭐

**项目实现**：



* 客户端按键后**立即本地表现并进入 CD**，不等服务器回包（手感）；服务器是最终权威，回包校正 CD/MP。

* 每次施法生成非零 `skill_uuid`，请求和服务器通知共用；`MSkillCore` 记录 `_latestSkillUuid`（只有最新施法能更新 CD 快照）和 `_latestResultUuid`（权威结果去重）。

* **旧回包不能覆盖新一次施法**（比如网络抖动，第 1 次释放的拒绝包晚到，不能把第 2 次已经成功的 CD 清掉）。

* 用 `attackSeq`（攻击序号）匹配客户端预测和服务器结算，避免重复结算。

* `MSkillPrediction` 记录单次预测：UUID、预测前 CD 截止时间、确认截止时刻（动作时长 + RO 2 秒宽限，用 `realtimeSinceStartup` **不缩放时钟**，避免 timeScale 影响 CD）。

**关键设计取舍（项目真实踩坑，绝佳 STAR 素材）**：



* **早期版本**做了 "逐笔预测确认队列 + 超时回滚 + 必须服务器 End 才回收实例"，后来按真实 RO 逻辑**删掉了确认等待**：本地立即表现 / CD，动作与 CD 允许即可续放，无回包不阻断；Core 只保留最近施法 UUID 用于迟到校正和结果去重。

* **另一个真实 Bug**：表现实例回池时 `Cease→Reload` 误清了角色 CD，导致 "10 秒 CD 的技能，0.5 秒表现结束后 CD 被清零、可无限释放"。根因是把 "正常表现结束归池" 当成了 "预表现失败"。修复原则：**角色 CD 只由施放写入、倒计时、明确清场和权威结果决定；表现回收 / 资源清理绝不能重置 CD；不等服务器确认 ≠ 不受 CD 约束。**

**追问**：



* 客户端预测的一般流程？预测 → 本地立即执行 → 发权威请求 → 收权威结果 → 对账（一致则保留，不一致则回滚 / 调和）。

* 为什么不做完整回滚（rewind+replay，如虚幻 / Overwatch 的 GDC 方案）？MMORPG 技能表现重、数量多、实时性要求中等，本项目选择 "轻量预测 + 权威校正最新值"，只对 CD/MP 等做调和，不做状态快照重放，是成本 / 手感的权衡 —— 要能讲清为什么这样选。

* 服务器拒绝了但客户端动画已经播了怎么办？本项目拒绝只结束匹配 UUID 的表现（Interrupted），以服务器为准；外观上可接受短暂预测。

* 确定性随机：战斗随机不用各方独立 `Random.Next`，而用 **战斗种子 + 攻击者 + 攻击序号 + 技能 ID + 命中序号** 组成确定性输入，两端算出相同结果（防作弊 / 可复盘）。

### 3.3 对象池与施法代次 ⭐⭐⭐

**项目实现**：



* `MCommonObjectPool<T>`（泛型、静态、每类型一个池，底层栈结构 `MObjectPool<T>`，借 `Get()` 还 `Release()`），技能实例、技能数据、计时器参数等高频对象全部池化，避免战斗 GC 峰值。

* `MSkillFactory` 统一借还技能；`MSkillCore` 用**引用计数&#x20;**`_ownerCount`（技能字典 + 存活施法实例共同持有，Retain/Release，最后一个释放触发回池）。

* **施法代次（FireGeneration）**：池对象被复借给新施法时递增代次；异步计时器回调、模型加载回调回来时核对 UUID + 代次，不匹配直接丢弃，**防止 "旧施法的延迟回调写到新施法对象上"**。Reset 时先注销计时器票据再更新代次。

**追问（Unity GC / 池化高频）**：



* 为什么战斗要对象池？Instantiate/Destroy、new List、闭包、装箱（boxing）、字符串拼接都会产生 GC 垃圾，Unity  Mono/IL2CPP 下 GC 会造成卡顿（尤其老版本 Boehm GC 不分代、STW）。技能特效 / 子弹 / 伤害数字是高频创建销毁对象，池化收益最大。

* 池化要注意什么？**取出必须完整重置状态**（本项目每个池化对象都有 Initialize/Reset，归还清 UUID / 时钟，防止借到脏数据）；**生命周期归属清晰**；**异步回调重入**（代次 / 令牌解决）；池不是越大越好，要设上限避免内存常驻。

* 引用计数 vs 池的关系？Core 被 "已学技能字典" 和 "正在播放的施法实例" 两处持有，用引用计数决定何时真正还池，避免播放中被复用。

* 还能举哪些 GC 优化？缓存 WaitForSeconds、用非分配物理 API（NonAlloc）、避免 foreach 在老 Unity 对部分集合装箱（本项目干脆规范禁用 foreach，统一 for + 快照列表）、字符串用 StringBuilder、Update 里避免 new。

### 3.4 技能时间线：MTimerMgr 与强类型事件 ⭐⭐

**项目实现**：



* `MArtSkill.Start` 只做 `base.Start()` + `FireEvents()`；`FireEvents` **一次性**把本次锁定的 FxEvents/AudioEvents/ChargeList 注册到 `MTimerMgr`（`SetTimer`，**整数毫秒**时钟，由实体 deltaMilliseconds 驱动），而不是每帧 Update 去扫描未来事件。

* 到期回调 `OnProcessTimer → InnerProcessTimer` 执行一条具体指令（放特效 / 播音效 / 启动位移）。

* 计时器票据 `AddedTimerToken` 管理，`KillTimerAll` 注销本次所有计时器。

* 载荷用具名强类型 `MSkillTimerArgs`（UUID + 施法代次 + 具体事件），**不用&#x20;**`object[]`（项目规范：业务事件禁止 object/dynamic/ 无约束泛型）。

* 零 / 过期事件同步补发（冷加载时按已累计时钟补发错过的事件）；正数事件至少 1ms 异步；同毫秒注册保稳定顺序。

**追问**：



* 为什么用整数毫秒而不是 float 秒？避免浮点累加误差、便于跨端对齐和网络同步、计时确定性。

* 为什么注册一次而不是每帧扫表？职责清晰、省每帧遍历、避免补播 / 重复触发；Update 只推进时钟和回收声源。

* 模型异步加载没好事件就到期了怎么办？通过 `MModel.AddLoadGoCallback` 登记待处理 GO 操作（暖加载同步返回零票据，冷加载返回可取消票据），模型加载完成（FinishLoad/PresentationReady）后**只补发已到期的 pending**；用加载会话（session）防止旧模型加载结果交付给新模型。AudioSource 必须挂 Transform，所以冷模型音效也要等 GO。

### 3.5 动画根运动 + 程序位移合并 ⭐⭐⭐

**项目实现**（本项目技术含量较高的一块）：



* 两种位移来源：

1. **动画根运动（Root Motion）**：接管 `Animator.applyRootMotion`，用 `SkillRootMotionCollector` 在技能占用且 clip 就绪时采集 `Animator.deltaPosition` 的 **XZ 水平分量**；

2. **程序位移（RO 的 ChargeList/ECharge）**：编辑器配的位移曲线（前向 / Self / 固定方向、水平累计），导出为 `MSkillChargeData`，经计时器到期交给实体挂接的 `MDisplacementComponent`，按冻结的全局毫秒原点求**累计曲线差量**。

* 最终由 `MMoveComponent` **独占提交**：把「玩家输入 + 重力 + 动画根增量 + 程序位移差量」合并，**一次** `MoveCharacter` 走 CharacterController 碰撞；侧向撞墙停止，不拉到终点。

* 程序位移三种裁剪策略：Clamp（钳制）/Stop（停止）/Continue（可回拉），`maxDistance` 前向硬上限；动画窗口与程序位移窗口重叠会拒绝（防双倍位移）。

* 位移组件由**实体**通过 `MComponentMgr.CreateComponent` 挂接（继承 EntityComponentBase），普通组件更新在 "优先阶段" 先推进位移，再跑专用 Move/Buff/Skill/Machine，保证同帧唯一提交、末帧 Move 先于 Skill 离槽，避免一帧滞后 / 双推进 / 末帧丢量。

* 翻滚滑步案例：复用 80 帧 @120Hz（667ms）的滑步动画，沿当前朝向，约 5 米距离通过根运动倍率（1.458485）校准，CD 0.5s、零耗蓝无伤害、白色网格残影（GhostEffect 30Hz 快照）。

**追问**：



* Root Motion 是什么、优缺点？动画自带位移，表现自然但不可控、网络难同步、容易穿模；程序位移可控可预测但要手调。本项目**两者并存且统一合并到一次移动提交**，是常见工业做法。

* 高速移动碰撞穿透怎么办？（你简历 / 偏好里关注过）CharacterController.Move 是扫掠（sweep）检测，连续碰撞一般不穿；但速度极高、单帧位移大于墙体厚度会隧道穿透（tunneling），对策：限制单帧最大位移、射线 / 胶囊扫掠预检测、减小物理步长、服务器校验位移上限（防加速挂）。本项目有 maxDistance 硬上限和侧撞停止。

* 位移为什么以服务器 / 冻结时钟为准？曲线求值用施法开始时冻结的时间原点，同步切段 / 换模型不能改变本次指令校验，防篡改和保证两端一致。

* 为什么只取 XZ？Y 轴交给重力 / 跳跃逻辑，避免动画根的垂直抖动和重力打架。

### 3.6 冷却（CD）系统 ⭐⭐



* `SkillCDGroupInfo` 同时维护**单技能 CD**（键 = 技能 ID）和**共享 CD 组**（键 = CooldownGroupId），CD/CurrentCD 单位秒，Get/Set/Clear。

* 已装备 Core 与组件共用**唯一 CD 记录源**（组件 SkillCDDic），Core 装配时把独立期剩余 CD 移交（BindCooldown），升级换 Core 不复制倒计时。

* CD 用 **realtime 不缩放时钟**递减，不用被 timeScale 缩放的实体 deltaTime，保证暂停 / 慢动作不影响真实 CD。

* 零 / 无效 CD 清除归池；重复设同值也校正剩余时间。

### 3.7 技能打断、状态门禁与规则配置 ⭐⭐



* `MSkillComponent.CanStart` 是**唯一施法门禁**：CD、MP、`Entity.IsJump`（起跳当帧到落地接地禁止普攻 / 技能，多段跳 / 下降都禁，不缓存空中输入）、施法规则统一在此判定；发包前和本地直接预测共用同一校验，被拒不扣 MP / 不开 CD / 不推进普攻段数。

* `SkillCastingRules.json` 由编辑器 `SkillCastingRulesConfig.asset` **同源导出到客户端和服务端**：`InteruptSkill`（新技能可打断哪些旧技能，服务器全部校验通过后才结束旧 UUID）、`MoveCasting`（客户端水平移动门控）。服务端只读部署目录 Config，不信客户端传的绝对路径 / 权限。

* 跳跃状态由移动组件起跳置位、接地 `EndJump` 清除；当前服务端无跳跃状态源，所以这是客户端门禁，不为此虚构协议（明确边界）。

### 3.8 技能生命周期与 "脱手" 管理 ⭐⭐



* `MSkillComponent.Update` 分两部分：当前主动作技能 OnUpdate，和常驻存活列表 `_skills`（独立运行 / 已离开主动作槽的技能，不能统称 "脱手"）。

* `MSkill.Update(float)` 返回 bool 表示存活；常驻列表**倒序**遍历，返回 false 就 `Cease(true)`（倒序是为了遍历中安全移除当前元素）。

* 自然结束 `ApplyServerEnd(false)`：动作可先退槽，但保留晚到计时器、已到期 GO 请求、完整音效尾巴和粒子尾迹，全部收尾后才回池；打断 `Interrupted=true` 立即注销。

* 预表现 2 秒 / 正式 10 秒存活上限（RO 规则），用累计技能时间，防泄漏。

* 粒子用**独立租约**持有运行资产到尾迹结束，不能因为技能回池就把还在飞的粒子卸载掉。

## 4. 技能编辑器（工具向，差异化亮点）⭐⭐



* 基于固定嵌入包 `com.ethan.act-action-editor`（YCombatEditor，MIT），适配 Unity 2023.2，保留独立程序集 `Ethan.ActionEditor.Editor` 和 GUID。

* 用 **ScriptableObject（SkillConfigSO）+ 自定义 Timeline 轨道**做技能编排：动画、特效（Fx）、音效（Sound）、位移、碰撞、飞行物、镜头、震屏、Buff 等轨道。

* 按 RO 真实 proto 扩展了 9 类制作轨道：Rotate、Shake、CameraFx、CameraPostEffect、ChangeColor、SkillBar、MobUnit、AIEvent、Buff；秒字段在 UI 边界投影到帧（FPS 换算）。

* 编辑期能力：暂停逐帧预览、粒子 / 飞行物按固定 FPS 时间步模拟、真实 PCM 音频波形包络绘制 + Alt 选点把特效触发帧和音频峰值对齐、特效播放范围估算（保守粒子寿命上界 + particleCount 归零判定有限收尾）。

* **制作范围与正式运行解耦**：编辑器支持很多轨道，但正式运行只导出 / 执行已接入的子集（单段动画、单次粒子、单帧音效、根运动窗口、程序位移）；未接入的非默认内容**阻止发布并报错**，而不是静默忽略 —— 避免 "编辑器里能配、游戏里不生效" 的坑。

* 导出契约：单次施法锁定表现行 ID / 动画 / 时长；`TimelineDurationSeconds`（制作末触发范围）与动画 `DurationSeconds` 分离，波形和粒子自然尾迹不延长制作 END；运行态 Inspector 禁用导出按钮，只能在编辑态显式导出。

**追问**：



* ScriptableObject 相比 JSON/MonoBehaviour 的优势？编辑器内序列化、类型安全、可挂资产引用（动画 / 特效 / 音频 GUID）、批量配置、内存单一实例；适合做策划配置。

* 自定义 Timeline/Playable 了解吗？PlayableAsset/PlayableBehaviour/PlayableTrack 一套，可做运行时行为；本项目编辑器更多是制作期数据产出 + 导出 SO/JSON。

* 怎么做编辑器和运行时职责分离？编辑程序集（Editor/）不进包、运行类型在 Runtime/、校验在独立 Verification 程序集；配置目录只存资产 JSON，逻辑源码在 Scripts/SceneEntity/Skill。

## 5. 移动同步与实体架构 ⭐⭐⭐

### 5.1 他机移动：影子跟随 + 插值 / 外推

**项目实现**（`FunlModule/Move/MoveComponent.cs`）：



* 收到服务器下发的他机目标点后，不直接瞬移，而是在 **0.15s 窗口（delay）内从当前位置平滑移动到目标点**（影子跟随），用累计 `_server_time` 归一化做插值。

* 转向：`MinRotationAngle=2°`（小于不转，防抖）、`MaxRotationAngle=90°`（大于直接转向不插值），中间用 Lerp/Slerp。

* `keep_moving` 标记：同步时对方仍在移动，则提前到达后**沿朝向外推（extrapolation）**，否则停步，避免他机一顿一顿。

* 走过头检测 `_lastDis` 防目标点附近来回抖动。

* 本机 `LocalSync` 自己模拟位置；`CostTime` 累计本机预测时间用于上行上报；传送带（Trigger 速度向量叠加）、`force_sync_pos` 一次性强制同步标志。

**追问（网络同步八股，结合项目答）**：



* **状态同步 vs 帧同步 vs 状态同步 + 预测**？本项目是**服务器权威的状态同步**：客户端上报操作 / 位置，服务器算权威状态并广播快照，客户端插值 / 外推。帧同步（Lockstep / 确定性帧同步）只传输入、两端各算各的，要求极强确定性、适合 RTS/MOBA/ 格斗，断线重连要追帧。

* **插值（interpolation）vs 外推（extrapolation）vs 回滚（reconciliation）**？插值是延迟 1\~2 个快照在过去两点间平滑（流畅但有延迟，用于他机）；外推是按速度方向预测未来（省延迟但转弯会错，用于持续移动）；回滚是本机预测和权威不一致时回退重放（用于本机玩家）。

* 为什么延迟缓冲是 100ms 左右？一个网络 RTT 和快照间隔量级，用一点显示延迟换平滑；MMORPG 可接受，FPS 对延迟更敏感。

* 怎么防加速 / 瞬移挂？服务器校验相邻两次上报的位移 / 时间得到速度上限，超阈值判定作弊（拉回 / 限速）；本项目服务端位移权威结算目前是边界（客户端主导水平移动），要能诚实说明现状和改进方向。

* 快照同步带时间戳，客户端怎么对齐？按服务器时间戳排缓冲，插值渲染过去～100ms 的状态；网络抖动用抖动缓冲（jitter buffer）。

### 5.2 实体 - 组件架构与统一实体世界 ⭐⭐



* `SceneWorldSystem` 是客户端场景实体唯一管理器，本地 `PlayerEntity`、其他玩家 `RoleEntity`、怪物 `MonsterEntity/BossEntity/EliteEntity`、NPC、宠物、子弹（Projectile/Rect/Ring/Anim/Target 多种形状）、陷阱、采集物等全部进同一个 `SceneEntityWorld`，按实体 ID 查询 / 移除；`Global.SceneWorld` 是进程级入口。

* 实体继承 `ROObject`；**运行时唯一身份是&#x20;**`ulong UID`**（= RO 的 uuid）**，`GetID()`/ConfigId 是配置表身份（怪物表 ID/NPC ID），RoleId 是持久化角色 ID，三者不能混；EntityId 只是 UID 的过渡别名。

* 组件由 `MComponentMgr.CreateComponent` 创建、进实体组件容器（`EntityComponentContainer`）统一生命周期 / 池回收；组件分类型枚举（追加 Displacement=32，Common/Net 两 DLL 同步）。

* 组件分 "普通组件" 和 "专用组件（Move/Buff/Skill/Machine 等）"，更新分阶段，位移在优先阶段。

* 实体之间的主人 / 目标 / 施法者关系（OwnerUID 这类）只能由业务组件存对方 UID，基础实体层不背关系字段。

**追问**：



* Unity 原生 GameObject/Component 够用为什么自研 ECS / 组件？①把网络数据实体和表现 GameObject 解耦，逻辑实体可池化、不依赖 Unity 生命周期、可做单测；②组件按职责拆分（移动 / 战斗 / Buff / 状态），避免巨型类；③和服务端实体结构对称，便于同步。这不是 Unity DOTS ECS，是**经典 OOP 组合式组件（组件容器 + 类型枚举）**，要主动说清区别。

* 实体池化要注意什么？隐藏 GameObject、重置状态 / UID / 代次、解绑组件引用、归还共享池；异步加载回调按会话 / UID 校验。

### 5.3 动作状态机 ⭐



* `MStateMachine`（RO 风格）：状态以 `StateDefine` 为键存 `MActionStateContainer`（按枚举和类型双向索引）；切换前 `StatePermitted` 做**状态权限校验**（什么状态能进什么状态，如死亡中不能放技能）；动作结束 / 被打断自动回默认（Idle）。

* 动画去重：`_isTriggered` 防同一帧多次 PlayAnim，`_preState` 记录上一动画状态避免重复切换；对象池复用时 `_registered` 防重复注册状态。

* 状态类型丰富：Idle/Move/Jump/BeHit/Dead/Stun/Climb/Fish/Sing/Dance/Collect/FearRun/Born/Skill 等。

**追问**：有限状态机 FSM 局限？状态爆炸、难处理并行动作；进阶方案分层状态机（HFSM）、行为树（BT，AI）、**动画状态机（Animator StateMachine）+ 游戏逻辑状态机分离**、效用系统 / GOAP。本项目逻辑状态机驱动，动画表现走 Animator Trigger。

### 5.4 附近玩家同步（AOI 雏形）⭐⭐



* 进入世界：先 `BroadcastRoleEnterWorld`（通知范围内其他人我上线），再 `SendNearbyRoles`（把范围内现有玩家发给我）。

* `IsNearbyRole`：先比 **MapId（同地图）**，再算 **三维距离 ≤ 100 米**。

* 技能广播也走附近快照（`BroadcastSkillNotice`），但注释明确 "广播范围 ≠ 权威命中范围"，命中判定另算。

**追问（AOI 必考，本项目是最简实现，要能讲演进）**：



* 现在每帧 / 每次事件全服遍历算距离，复杂度 O (n²)，人少可以，人多爆炸。

* 标准 AOI 方案：


  * **九宫格 / 格子（Grid）**：地图切格子，只遍历所在格 + 周围 9 格，实现简单、最常用，进出格子触发事件；

  * **十字链表（链表法，如老一代梦幻 / RO 类）**：x、y 各一条有序链表，移动时调整顺序，O (1)\~O (n) 找视野内；

  * **四叉树 / 八叉树**：空间递归划分，适合不均匀分布；

  * **灯塔（Tower）/ 区块订阅**：按区块发布订阅。

* 还要处理：进入 / 离开视野的 enter/leave 事件、裁剪（同屏人数上限、LOD）、分线分房。

## 6. 资源管理与热更新 ⭐⭐



* **YooAsset**：资源打包 / 版本 / 热更 / 加载封装。`ResourceMgr` 按路径缓存 Prefab / 特效 / Sprite 的异步句柄（Handle），`LoadAssetAsync`；图集先 `CheckLocationValid` 判断虚拟切片路径，无效则走图集 `LoadSubAssetsAsync`，避免无效地址报错。

* **HybridCLR（原 huatuo）**：纯 C# 热更方案，把业务逻辑放热更 DLL，无需 Lua；原理是给 IL2CPP 补充元数据（AOT dll 加载为解释执行元数据），让泛型 / 反射等 AOT 不支持的代码热更后也能跑。

* 启动流程在 `Assets/Boot`（Load.cs/ HotUpdateView）：初始化 YooPackage → 检查版本 / 热更资源 → 加载热更程序集 → 进主游戏。

* 技能表现资源有独立缓存层 `SkillRuntimePresentationCache`：资源包就绪由 `NotifyResourcePackageReady` 通知，暖加载（已就绪）同步、冷加载终态一次通知、失败给空值通知；技能实例不轮询资源。

**追问**：



* YooAsset/Addressables 相比 Resources 的区别？Resources 整包打入、启动全量索引、内存难卸、不能热更；可寻址资源系统按需打包、引用计数、支持远端下载和依赖管理。

* 资源加载为什么要缓存句柄？YooAsset 用引用计数，Load 一次要对应 Release，否则资源不卸载造成内存泄漏；同一资源多处用要共享 Handle。

* 热更方案对比？Lua（xlua/tolua，成熟但要维护两套语言 / 类型）、ILRuntime（C# 解释器，性能弱）、HybridCLR（C# 原生 + 解释补充，性能接近原生，现在主流）、资源热更（美术 / 配置）vs 代码热更（DLL / 脚本）。

* 首包 / 分包、CDN、版本清单（manifest）、断点续传、校验 MD5 是资源热更常聊点。

## 7. 服务端数据与基础设施 ⭐⭐

### 7.1 分布式 UID（雪花算法变体）⭐⭐



* 公共库 UID 是正数 long，位布局：**UIDType 3 位 | 自定义纪元毫秒 40 位 | 逻辑服实例 ID 8 位 | 同毫秒序列 12 位**。

* 纪元固定 `2025-01-01 UTC`；每进程启动显式配 0\~255 实例 ID；进程内用锁处理并发、时钟回拨、序列耗尽。

* 分类只用 Item/Shop/Reward/Pet/Mail/Common，保留值和 Max 禁止生成。

**追问（雪花算法 Snowflake 八股）**：



* 经典雪花：1 符号 + 41 毫秒 + 10 机器（5 数据中心 + 5 机器）+ 12 序列，理论 4096/ms/ 节点。

* 为什么这样分位？毫秒高位保证时间趋势递增（利于 B+ 树索引）、实例位隔离不同进程避免冲突、序列位扛同毫秒并发。

* **时钟回拨怎么办**？拒绝生成并等待 / 报错、用历史最大时间戳、或换备用节点位；本项目生成器内处理。

* 40 位毫秒能用多久？2^40 ms ≈ 34.8 年；12 位序列每毫秒 4096。

* 为什么实例 ID 不能重复？两节点同毫秒同序列会撞 ID，要靠注册中心 / ZooKeeper / 配置分配保证唯一。

* 现状注意：物品 ItemUID 当前仍是 int32，long UID 未直接接库，迁移要单独立项 —— 体现你清楚技术债边界。

### 7.2 Redis / MySQL / SqlSugar 与背包事务 ⭐



* CenterServer 负责持久化，MySQL 存角色 / 背包等，SqlSugar 是 ORM；Redis 做缓存 / 加速。

* 背包按 `KnapsackType` 分**四类独立可扩容容器**：普通 / 装备 / 消耗品 / 材料，新角色各默认 81 格；穿戴栏 `RoleCurrtEquipPack` 不参与扩容；普通背包不再聚合其他三类。

* 扩容：请求必须带背包类型，**逻辑线程**校验档位 / 上限 / 扣费事务，只改指定类型，再同步 Center 持久化；容量字段语义是 "已开格数" 不是 "物品数量"。

* 网络回调不能直接改背包，必须进主循环消费者执行。

**追问**：



* 为什么背包拆分独立容器而不是一个大背包？业务隔离、扩容独立、查询清晰、避免单表 / 单容器热点。

* 扣费 / 发货事务怎么保证不丢不重？扣货币和发道具要在一个事务，失败回滚；项目代码评审曾发现 "购买无回滚" 疑似缺陷，可作为风险意识素材。

* Redis 和 DB 一致性？Cache Aside（先更新 DB 再删缓存）、登录加载、定时 / 下线落盘；MMO 常用 "内存权威 + 定时存档 + 关键操作立即落库"。

* 道具实例用 UID 还是堆叠？可堆叠物（消耗品 / 材料）按类型 + 数量，不可堆叠（装备）用唯一 UID + 词条 / 强化数据。

### 7.3 定时器



* 服务端 `CTimerMgr` 在每个逻辑帧 `Update(50)` 推进，角色保存等业务实现 ITimer 回调；Buff/CD 用服务器 Tick 而非客户端时间。

* 客户端 `MTimerMgr` 用整数毫秒、实体帧驱动，技能时间线用。

* **追问**：定时器实现（最小堆 / 时间轮 TimingWheel）？海量定时（Buff 到期）用层级时间轮 O (1) 增删；为什么不能用 `Thread.Sleep`/ 大量 `Task.Delay`—— 不可控、不随逻辑帧暂停、难重放。

## 8. 工程规范与质量（体现工程素养的加分项）⭐



* **强类型事件载荷**：业务事件 / 接口禁止 object/object \[]/dynamic/ 无约束泛型，必须具名 IEventArg 实现（如计时器 MSkillTimerArgs、输入轴、相机目标变更各一个类型）；object 只允许在反射 / 序列化 / 第三方适配边界并注释。

* **禁用三目运算符**（统一 if/else 便于审查）、**禁用 foreach**（统一 for；字典等先拷快照 List 再索引遍历，引用类型元素改成员生效、替换元素不回写原容器）、**禁止 namespace 块**（类型全局命名空间，项目特定规范）。

* **一类一文件**（顶级类 / 接口 / 枚举 / 委托同名文件）、全中文注释（字段要写语义 / 单位 / 生命周期）。

* **测试纪律**：Mock / 测试按钮只能在测试脚本和专用测试组件，禁止挂正式场景 / 预制体；独立 Verification 程序集做合同测试；改完必须编译 + 静态校验 + 记录 TEST\_REPORT。

* **变更管理**：SHA 审计（编译输入文件哈希一致性）、冻结 before 再改、保护未授权文件、临时文件统一 `_temp`、修改日志和设计文档分目录归档。

* 这些在面试里能体现：**代码审查意识、防御性编程、确定性、可测试性、多人协作规范**。即使你不完全认同某些规范（如禁 foreach/namespace），也可以说 "这是团队为了统一风格和静态审查定的约束，我理解其成本并遵守"。

## 10. 可直接讲的项目难点 / STAR 素材（建议背 3\~4 个）



1. **技能 CD 被误清零导致无限释放**（定位 + 根因 + 最小修复）

* S/T：参考 RO 移植技能脱手生命周期后，测试发现 10 秒 CD 技能可连续释放。

* A：独立复现（0.5 秒表现、0.61 秒正常回池后 CD 变 0、第二次按键成功发包），定位到 `Cease→Reload` 把 "正常表现结束归池" 当成 "预表现失败" 而清 CD；最小删除该联动，不引入确认队列 / 快照。

* R：明确 "CD 只由施放 / 倒计时 / 权威结果 / 明确清场决定，表现回收不清 CD"，20 次连按在 CD 内被正确阻断，回归通过。体现**先复现、找根因、最小修复、不堆砌防御机制**。

1. **网络线程与逻辑线程分离的命令队列设计**

* 讲不可变 GameCommand、ByteString 拷贝、ConcurrentQueue + Interlocked 计数、容量背压（20000/3000）、固定 20Hz + 最多追 5 帧、异常隔离、断开事件也排队。能延展聊 Skynet actor、无锁化、螺旋死亡。

1. **动画根运动与程序位移合并、防双推进 / 穿墙**

* 讲两类位移来源、位移组件实体挂接、更新阶段顺序（位移优先、同帧唯一提交、末帧 Move 先于 Skill 离槽）、曲线冻结时钟求值、三策略 + maxDistance、翻滚 5 米倍率校准。延展高速穿透与服务器速度校验。

1. **池化对象的异步回调重入（施法代次 / 加载会话）**

* 讲技能实例池复用后，旧计时器 / 旧模型加载回调可能写到新施法；用 UUID + 施法代次 + 模型加载会话三重校验，Reset 先注销票据再换代次，自然结束保声尾、打断立即清。延展到客户端连接代次（同一思想）。

1. **技能编辑器制作范围与运行时解耦**（投工具 / TA 岗好用）

* 讲扩展 9 类 RO 轨道但运行时只执行接入子集、未接入内容阻止发布、波形对齐触发帧、粒子有限收尾判定、编辑 / 运行 / 校验三程序集分离。

1. **TCP 自定义帧拆包**（基础但人人能问）：2 字节长度头 + 累积缓存 + 半包保留 + 超长保护，能徒手写出循环拆帧伪代码。

## 11. 可能被问的 "项目不足 / 你怎么改进"（提前准备，显成熟）



* 发送是同步 `Socket.Send`，高并发应改异步发送队列 / 双缓冲 IOCP；APM 可迁移 SAEA 降低分配。

* AOI 目前是全量遍历 + 100 米距离判断，应上九宫格 / 十字链表并产生 enter/leave 事件。

* 水平移动权威主要在客户端，服务端缺位移 / 速度上限校验，存在加速挂风险，应补服务器速度阈值与拉回。

* 跳跃状态服务端无源，门禁只在客户端；要做空中技能 / 网络一致需同步跳跃状态协议。

* long UID 尚未全量接库（物品仍 int32），需要迁移计划。

* 代码评审发现的若干疑似缺陷（背包扩容缺格重复累加、会话泄漏、购买无回滚）应单独立项 + 加集成测试。

* 没有真正的命中 / 伤害权威结算与战斗回放（确定性随机框架已设计但需落地）。

> 讲不足的技巧：先说清 "当前是什么、为什么这样（阶段 / 成本）、如果继续做我会怎么演进"，把不足讲成有规划的技术债，而不是不会。
