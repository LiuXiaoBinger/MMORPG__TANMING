# MMORPG 功能完成度与开发优先级

盘点日期：2026-10-23

适用范围：`D:/unitypro/LYFMMORGP` 当前工作区。本文只依据现有源码、协议注册、配置和已有验证记录判断完成度；有界面、枚举、配置或测试替身但没有可执行业务闭环的功能，按未完成或部分完成处理。

## 结论

项目已经具备“登录进入主城、角色移动、技能表现、背包和商城基础链路”的客户端/服务端骨架，适合继续做可玩的单地图战斗切片。距离市面上可持续运营的 MMORPG，最大缺口不是装饰性 UI，而是服务端权威玩法闭环：任务、装备成长、怪物战斗与掉落、组队副本、聊天服务和重连弱网。

建议顺序：先补齐双客户端可重复联机和服务端权威战斗基础，再做任务与装备成长，之后扩展组队副本和社交系统，最后处理运营型系统。

## 明确缺口

### 任务系统

已有任务枚举或配置线索，但 `LYF_Server/GameServer/MessageHandler/Task/.gitkeep` 目录没有任务 Handler，当前没有可核验的接取、追踪、目标进度、完成、提交、奖励、放弃和持久化协议。客户端也没有确认过任务列表、任务追踪和奖励领取的完整窗口/协议闭环。

任务是 NPC 导航之后最直接的可玩内容，应作为第一批成长系统开发。

### 装备、物品使用与属性成长

客户端已有 `BagWearItemTransition`，但服务端同名流程在 `LYF_Server/GameServer/Service/item/BagTransition.cs:510-544` 仍返回 `NotImplemented`，并且物品目录 `MessageHandler/Equip/.gitkeep`、`MessageHandler/Item/.gitkeep` 没有业务 Handler。缺少穿脱协议、装备栏权威状态、属性重算、使用/消耗、装备变化广播、存档和重登恢复。

### 怪物战斗闭环

当前能看到怪物实体、目标选择、技能表现和战斗组件基础，但未发现一条完整且可验证的“服务端受击判定 -> HP 扣减 -> 死亡 -> 经验/掉落 -> 客户端刷新 -> 持久化”链路。没有这条链路，任务击杀和装备掉落也无法落地。

### 多人社交与组队内容

未发现组队邀请/确认/队长/离队/队伍同步的完整协议与 Handler；公会、好友、邮件、排行榜、成就、拍卖、PVP、正式副本等也未发现可验收的端到端业务闭环。相关枚举、UI 或配置只能作为预留，不能当作已完成。

### 聊天服务

`MainCtrl.OnChatSendRequested` 当前直接调用 `_chatWindow.AppendMessage`，并在 `MainCtrl.cs:360` 注明聊天协议尚未接入。需要频道、长度/频率限制、服务端广播、跨地图范围、离线/系统消息和客户端收包刷新。

### 账号与运行稳定性

需要补齐断线重连、登录态恢复、重复登录处理、KCP/TCP 通道重建、场景切换、服务端权威位置校验、异常包和限流。当前隔离回环通过不能替代真实双客户端、弱网和发布包验收。

## 优先级

### P0：先让核心切片可长期测试

1. **正式双客户端联机验收**：同地图互见、移动/技能 KCP、服务器坐标权威、断线重连、弱网、跨场景和热更程序集版本一致。
2. **战斗最小闭环**：服务端目标合法性、技能命中/伤害、HP/死亡、复活或回城、经验和最小掉落。
3. **导航边界**：NPC/任务导航失败反馈、可达性检查、到达距离和障碍后的停止；暂不扩展服务端 A*，先把服务端位置校验和客户端路线失败处理做实。

P0 完成标准：两个打包或同版编辑器客户端能在同一地图连续战斗 30 分钟，断线重连后位置、技能冷却、背包和角色状态一致；服务器日志能解释拒绝的移动、技能和掉落请求。

### P1：形成任务驱动的成长循环

1. **任务系统**：接取、追踪、目标进度、NPC 提交、奖励、前置条件、放弃/失败、存档和重登恢复。
2. **装备和物品使用**：穿脱、属性重算、装备变化同步、消耗品、堆叠、背包容量和持久化。
3. **怪物掉落与奖励**：掉落表、拾取权、队伍归属、重复领取保护和任务事件通知。
4. **组队和副本最小版本**：邀请/确认/离队、队伍状态、实例地图进入/退出、队伍战斗奖励。

P1 完成后，玩家应能“接任务 -> 导航到目标 -> 战斗 -> 获得掉落/经验 -> 回 NPC 交任务 -> 装备成长”。这条循环比继续增加 UI 页面更能验证项目是否进入 MMORPG 可玩阶段。

### P2：补齐社交和运营能力

公会、好友、邮件、排行榜、成就、拍卖行、PVP、组队匹配、活动日历、GM/运营后台、完整设置和数据统计。这些系统依赖 P0/P1 的角色、物品、奖励和消息基础，过早开发会反复改协议。

## 开发顺序与边界

1. 固定并验收 P0 的协议和服务端权威规则，保留客户端导航作为输入表现，不把客户端路线当作服务器可信结果。
2. 先做任务协议和服务端任务状态，再接 NPC 对话/导航入口；任务奖励只调用已有背包事务，避免复制物品写入逻辑。
3. 在任务击杀事件稳定后接装备/物品 Handler 和属性重算，再接掉落与奖励存档。
4. 任务、战斗、背包和装备形成单人闭环后，再设计组队副本和多人奖励归属。
5. 最后接聊天、公会、邮件、排行榜和运营系统，并为每个系统补协议注册、Handler、客户端收发、存档和双客户端验收。

## 本次盘点的限制

- 本次是源码、协议注册和已有专题报告的静态盘点，没有修改业务代码，也没有把 UI 截图、配置表、枚举或隔离夹具当成完整功能。
- 未执行 Unity 现场画面、打包客户端双开、真实弱网、完整服务器部署或生产数据库验证，因此 P0 的运行稳定性仍需专项验收。
- 服务端是否最终需要运行时 A*，要按反作弊和移动权威方案单独决策；当前结论只说明现状是客户端 A*、服务端无运行时寻路。
