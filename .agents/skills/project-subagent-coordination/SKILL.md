# 项目子 Agent 协作

本 Skill 集中本项目的子 Agent 选择、派工、续作和验收细则。开始前遵循项目根目录 `AGENTS.md`；桌面入口和参数以 `AIconfig/agent/workbuddy_executor.md`、`AIconfig/agent/doubao_executor.md` 为准。用户本轮明确指定的模型和安排优先于默认偏好；AGENTS 中已授予的项目权限不扩大任务文件范围或业务目标。

## 模型与分工

- 选择顺序：用户本轮指定优先；其次，按 Asia/Shanghai 本地时间，23:00（含）之后优先将可由 WorkBuddy 承担的任务交给 WorkBuddy；其他时段再按任务类型和下列默认分工选择。任务授权或服务可用性不支持 WorkBuddy 时，按已有项目流程选择替代执行者并记录原因。
- 轻量、范围明确且预期一次完成的查找、小改动、注释或中文记忆同步，默认优先调用本机 Ollama 的 `qwen3:8b-light`。最多执行一次；不可用、输出不完整或验收不通过时，按项目规则转交外部执行者，不静默换成其他 Qwen 标签，也不重复返工。23:00 后的 WorkBuddy 优先规则优先于此默认偏好。
- WorkBuddy 承担授权范围内的项目开发与修复；创建任务时，在模型菜单选择 `Hy4 preview`，仅当界面仍标记“夜间免费”时将其作为免费模型偏好。选择动作发生在新任务创建阶段；不要在执行中的任务上远程切换模型，也不要因等待超时另建任务。
- 豆包承担代码/参考项目查找和 Bug 定位，也可按主 Agent 明确授权承担开发。新建或续发本项目任务时显式指定 `豆包 2.1 Pro`；桌面 CLI 使用 `--model "豆包 2.1 Pro"`，并沿用 `D:/unitypro/LYFMMORGP`、项目 ID `38435310952198914` 和本地运行方式。模型不存在或不可选时如实报告，不要静默降级。
- Qwen 是本地 Ollama 外部模型；WorkBuddy 和豆包是各自桌面客户端/网关中的外部开发 Agent。不要把它们称为 Codex 原生子 Agent，也不要因为使用 Skill 就自动增加委派对象。
- 每次实际调用子 Agent，都记录提供方和实际模型的完整名称/标签，以及任务或会话标识；同一会话若确实更换模型，按每次执行分别记录。界面或服务未披露实际模型时，明确记录“未披露/无法确认”，不得根据默认设置推断。

## 运行窗口与可见状态

- 派发子 Agent 前，先打开或选择该执行器对应的原生桌面工作窗口；提交后把窗口、任务页或状态面板的可用入口交给用户并保持可访问，执行期间不要主动隐藏或关闭。WorkBuddy 和豆包使用各自官方桌面工作任务入口，遵守其现有 Skill 的本地项目和原生会话要求。
- 执行器支持实时窗口时，优先展示能看到任务进程和结果的原生窗口；只读等待期间保留任务标识，状态变化时更新同一入口。不要为了展示而另建任务、切换项目或启动第二个同工程实例。
- 执行器不提供实时操作画面时，必须明确告诉用户实际可见范围，并展示可用的 Hub 任务状态、原生任务页或终端输出。Qwen 的 Ollama 调用没有原生 Agent 操作窗口，可展示其调用终端或状态输出；不得把 Hub 状态页、日志或模型自报描述成实时操作画面。
- 子 Agent 完成、返工或阻断后，保留结果入口和任务/会话标识，便于用户查看交付证据；关闭窗口前先确认结果已记录，且不影响原任务恢复。

## 派工与验收

- 主 Agent 负责理解需求、确定业务流程和验收标准、选择执行者、最终核对与项目集成。根据任务性质委派：查找与 Bug 定位走豆包既定入口，授权代码实现优先 WorkBuddy；用户明确安排优先。
- 查找、参考项目调查与 Bug 定位默认由豆包承担只读调查；先给出问题、范围与所需证据，不授予业务修改权。交付需包含精简路线、路径/行号、调用链和依据；Bug 还需真实复现步骤、现象或日志。
- Codex 按调查路线核对真实文件和调用关系，只补读必要证据与测试，不重复全量搜索。路线错误或证据不足时，附上核验发现沿原任务补充；已受理超时先恢复原任务。已核验的调查结论及路径交给 WorkBuddy 实现，不要求其重新扫描全项目。
- 派工单写明问题/目标、允许修改的逐项文件、已知证据、验收条件，并附项目目录、分支、实际基线、任务/会话标识和交付格式。只读查找不授予文件修改权，任务授权不扩大到未列范围。
- 子 Agent 先自检并交付实际文件清单、检查命令/结果和未解决事项。主 Agent 核实磁盘差异及关键证据后执行必要验证；不能用模型自报完成代替验收。
- 测试失败且修正方向明确时，把复现步骤、真实失败证据和预期结果交回原任务返修，再由主 Agent复测。等待、连接故障、状态查询、自检和主 Agent 核验不计入开发轮次；保持原任务身份和计数。
- 豆包与 WorkBuddy 对同一问题各最多七轮（首次一轮加六次返修）。一个执行者满七轮仍失败后，按项目规则转交另一个；两者各满七轮仍未解决时，主 Agent 才可依授权接手。用户明确要求提前接手时遵从用户安排。
- 当上下文过长、反复压缩或影响准确续作时，为后续执行开启新窗口/会话。派发新执行前先读取原任务的相关对话、交付和最新状态，确认原执行已结束或明确交接；再把目标、授权文件范围、证据、当前模型、任务/会话身份、真实轮数和未决事项摘要带入新窗口。不得只凭旧摘要猜测，也不得让旧任务与新窗口同时修改同一文件；更换窗口不重置任务身份或轮数。
- 每次任务和返工都更新记录，写明实际模型、执行任务/会话与真实轮次。交付前按 AGENTS 维护英文协作记录、中文同步、项目修改日志和必要验收证据；由主 Agent 统一执行允许的 Git 集成，保留无关用户改动，不合并到 `main`。

## 不适用

纯原理问答、没有项目派工的普通代码工作、或用户明确要求 Codex 自行完成且与子 Agent 无关时，不要仅因本 Skill 可用而强行派工。
