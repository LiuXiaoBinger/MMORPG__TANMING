# LYFMMORGP 项目协作流程与分工边界

本文件是 AIconfig 内部的角色协作准绳，主 agent 依据此文件调度子 agent。
所有角色执行任务前必须先读本文件，确认自己的职责与流程位置。

| Codex 主 Agent | AGENTS.md 与本流程 | 解读需求、设计开发逻辑、发布任务、最后测试与失败退回 |

## 豆包与WorkBuddy桌面工作任务委派

1. Codex为主Agent，解读需求、设计开发逻辑并发布任务；豆包和WorkBuddy均为开发子Agent，继承 `AGENTS.md` 与对应开发角色约束。使用官方桌面的工作模式／工作任务，项目固定 `LYFMMORGP`、本地目录 `D:/unitypro/LYFMMORGP`，不派普通对话或其他项目。
2. 豆包只经 `E:/doubao-cli/doubao-windows.cmd`，新建和返工明确传 `--runtime local --project 38435310952198914 --workspace D:/unitypro/LYFMMORGP --permission AskOnRisk`；从CLI项目列表及任务上下文核对本项目。桌面工作路径启用原生agent_mode，不传headless专用mode work，不走网页或云电脑网页入口。
3. WorkBuddy按 `workbuddy-executor` Skill 优先经Agent Hub，传 `provider: workbuddy` 与本项目workspace；兼容直连也核对同目录原生工作会话的sessionId。不得使用网关源码目录或历史隔离测试会话。
4. 任务单说明标识、开发角色、分支及基线、逐项文件范围、需求、验收和交付格式。保存豆包conversationId/runId或WorkBuddy Hub/task/session编号，返工沿原任务提供失败证据；已受理超时恢复原任务，不盲目重发。
5. 开发子Agent可直接修改授权本地文件并先自检，Codex主Agent最后核对差异、产物并测试；不通过时附失败证据、复现步骤和预期结果返回原开发子Agent重新开发或修复，再由Codex复测，不通过不标验收完成。仅交付补丁时本地开发子Agent核对基线落盘，主Agent不代写业务代码；通过后统一记录、集成、提交推送功能分支，不合main。入口不可用如实记录，不回退网页或普通对话。

细则见 `AIconfig/agent/doubao_executor.md`、`AIconfig/agent/workbuddy_executor.md`；本段替换旧网页云电脑委派流程，历史实验不作当前入口。

## 查找与 Bug 排查先豆包后 Codex 核验

1. 代码、参考项目查找或Bug定位默认由Codex限定问题、范围与证据要求，先派豆包执行本项目官方桌面只读工作任务；用户另有明确分工时优先遵从。不同时自行做同范围完整搜索，减少Codex额度消耗。
2. 豆包交付精简查找路线、真实文件路径和行号、关键函数/调用链、结论依据与未确认项；Bug附实际复现、现象或日志。仅查找不得自行改业务或修复。
3. Codex先顺着该路线读取文件并核对证据，执行必要验证；成立后沿用结果，不从头全量重查。发现路线错误、证据不足或结论不成立时，再由Codex独立查找并记录纠正，最终结论仍由Codex负责。
4. 豆包已受理超时恢复原任务，入口不可用按既有桌面规则记录阻断，不伪称成功。后续业务修复仍走开发子Agent和最终验收流程；协作入口读取、约束和记录维护本身无需派查找任务。

## 标准执行流程
1. **解读需求**：Codex主Agent明确用户目标、范围、优先级和验收标准，必要时协调产品经理补充信息。
2. **设计开发逻辑**：Codex主Agent明确业务流程、现有接口、修改文件和任务拆分，必要时采纳策划／架构建议，不扩大用户范围。
3. **发布开发任务**：Codex向对应开发子Agent（含WorkBuddy、豆包）派发任务，指定本项目、分支、基线、文件范围和验收要求。
4. **开发与自检**：子Agent修改授权本地文件并执行自检，交付文件清单、产物和实际结果；协议变更先更新 `LYF_Server/ProtoBuf/proto`。
5. **最后测试与审查**：Codex核对实际文件，执行必要编译、静态检查或运行测试，结合测试／审查角色证据作最终验收，结果写入 `Docs/AI/TEST_REPORT.md`，不只接受子Agent自报完成。
6. **失败退回并复测**：未通过时Codex沿原任务发送失败证据、复现步骤和预期结果，原开发子Agent重新开发或修复并交付，再回第5步；主Agent和审查员不代改业务代码，未通过或受阻如实保留未完成状态。
7. **验收与集成**：测试通过后Codex统一验收、维护协作记录、集成并按功能分支约束提交推送。

## 分工边界（谁干什么）
| 工作 | 负责角色 |
|---|---|
| 需求解读、开发逻辑设计与任务发布 | Codex主Agent，必要时协调产品经理／策划与架构角色 |
| 玩法、数据表和协议设计细化 | 策划与系统架构师提供建议，由Codex明确本轮方案和任务范围 |
| 客户端实现、修复与授权本地文件修改 | 对应开发子Agent，含WorkBuddy和豆包 |
| 服务端实现、修复与授权本地文件修改 | 对应开发子Agent，含WorkBuddy和豆包 |
| 最后测试与验收结论 | Codex主Agent，测试工程师可协助提供编译、联调及回归证据 |
| 代码质检 / 打回 | 审查员 |
| 测试失败后的重新开发或修复 | 返回原开发子Agent，完成后由Codex复测 |
| 集成验证与功能分支提交推送 | Codex主Agent；合入main仍需用户明确要求 |

## 规则
- **逐项交付文件**：每次代码修改后的回复与 `项目修改日志/` 必须列出新增、修改、移动、删除的文件及各自用途、具体变化；Unity `.meta` 可随对应文件列出，不用功能概括代替清单。
- **功能分支与上传**：当前功能开发在 `codex/feature-development`，后续分支沿 `codex/` 前缀。仅用户明确要求时才合入 `main`，普通开发、提交和推送授权均不含合并授权。检查通过后由主 Agent 检查暂存范围、提交本次任务文件与日志并推送当前功能分支，不混入无关用户改动、不强推；失败如实报告。
- **提交记录**：中文 Git 提交正文包含修改内容、验证结果和日志路径，类型前缀可沿 conventional-commits；项目修改日志记录分支、提交范围及推送结果，最终回复报告提交号与上传状态。
- **UI 融合沿现有模式**：新增或移植界面沿 View、WindowBase、WindowType 和既有 Ctrl 管理窗口，窗口/Widget 负责展示交互、控制器处理业务协议；不另建 UI 管理器或复制参考 Lua 框架。用户只要求界面时，仅接打开、关闭、分页、滚动等必要交互，不顺带实现选项业务效果。正式控件与引用存于预制体，复用本项目字体、层级和视觉资源。
- **项目难点持续沉淀**：遇到特别难实现、难复现、跨模块联动或多次排查与方案取舍的实际问题，参与角色必须提供事实，主 Agent 同步新增或更新 `项目分析/项目难点.md` 对应独立条目；未解决先记现状，后续补结论。记录背景、难点、证据与失败尝试、根因、方案取舍、关键文件、验证边界、未解决事项和面试讲述/追问；不虚构个人贡献、收益或上线结果，已有专题用项目根相对路径引用。任务收尾检查是否已沉淀，不能仅以对话或修改日志代替。
- **连续判断最多三个**：后续新增或修改代码的单个布尔表达式，`&&`、`||` 组合的判断项最多三个，混合或括号合并统计。超过时拆清晰分支或具名条件，保持求值顺序、短路与业务语义；不以换行规避、不新增多余判断，未经用户另行要求不批量改既有代码。开发和审查均遵守。
- **严格执行用户范围**：用户让做什么就做什么；主 Agent 和所有子 Agent 不自行扩功能、不顺带重构、不设计额外框架或未来需求，只做当前要求必需的最小适配。不得以完善性、稳健性或未来用途扩大开发和审查范围。
- **简单业务保持简单**：按当前真实需求实现最短正常流程；无用户要求或已复现故障，不添加额外校验、身份/状态门禁、代次、请求队列、重试、确认等待、多层空值判断或异常包装。现有接口的实际完成结果与必要接入可以处理，不以人为检查阻止正常业务；审查不得因假设情形强加这些机制。
- **参考移植优先照原代码**：用户指定参考项目时，沿用其代码结构、接口、职责和调用时序，仅做当前工程必要的最小接入适配；不得自行扩展功能、通用管理层或防御包装。额外功能由用户明确提出后再实现。
- **按真实需求审查**：先审核参考一致性和简洁性，不为无生产依据的假设重入/极端测试增加快照、代次包装、等待确认、重试或额外状态；已复现的实际问题只作有依据的最小修正。
- **一类一文件**：每个顶级类、接口、枚举和委托必须独立放置在一个同名源文件中；禁止通过聚合文件定义多个业务类型。
- **主 Agent 边界**：主Agent使用Codex，负责解读需求、设计开发逻辑、发布任务、最后测试验收和更新记录；测试不通过返回原开发子Agent重新开发或修复后复测，不直接修改客户端或服务端业务代码。
- **代码委派**：涉及业务源代码的新增、删除、重构和修复，必须交由对应客户端或服务端开发 Agent 执行；主 Agent 只能修改协作配置和记录文档。
- **强制创建子 Agent**：凡涉及客户端或服务端业务代码，主 Agent 必须先创建并委派对应开发子 Agent；豆包或WorkBuddy按照上述流程建立的本项目桌面工作任务属于明确的外部开发委派，可在授权范围直接修改本地文件；仅交付补丁时由本地开发子Agent落盘，不得以主Agent临时代改替代委派。
- 谁的问题谁修，审查员不代改
- 协议变更必须先改 `LYF_Server/ProtoBuf/proto` 再生成代码和进入开发，禁止先写业务代码后补协议
- 每个任务默认最多 3 轮审查；超出由主 agent 决策
- 代码审查通过前，禁止声明"完成"
- 每项工作开始前读取 `AGENTS.md` 和 `Docs/AI` 四份记录；结束后更新 `CURRENT_TASK.md` 与 `TEST_REPORT.md`
- 所有项目修改（代码、配置、协议、表格、资源、场景、工具或文档）的修改说明统一写入项目根目录 `项目修改日志/`；项目解析、参考项目分析、架构设计、功能方案和专题使用说明统一写入项目根目录 `项目分析/`；不得在根目录或 `Docs/AI` 散落创建这些文件。
- `Docs/AI/` 仅维护四份协作入口记录，专题分析正文不放在其中；文档引用一律使用项目根目录相对路径。
- 新增或修改业务代码时，开发者必须为类型/接口、函数（含构造函数）、字段、属性、常量、事件、参数及局部变量补充具体中文注释；审查员必须将注释完整性作为代码规范门禁
- 任务结束后，参与角色必须输出变更摘要或分析结论，审查员输出审查结论，二者并存留痕
