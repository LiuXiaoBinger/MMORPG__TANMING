# LYFMMORGP 项目协作流程与分工边界

本文件是 AIconfig 内部的角色协作准绳，主 agent 依据此文件调度子 agent。
所有角色执行任务前必须先读本文件，确认自己的职责与流程位置。

## 2026-10-23优先规则：轻量先Qwen，Agent读英文记忆

- 范围明确的轻量查找、注释、少量文件小改动、中文记忆同步统一使用本地 `qwen3:8b-light`，显式传完整模型名，不静默改用 `qwen3:8b` 或 `qwen3:8b-cpu`；一次实际尝试失败/不完整/验收不通过或连接不可用，立即交豆包查找或WorkBuddy修改，不反复要求Qwen返工；Qwen不计入两模型各7轮。复杂任务保持下方原分工。细则见 `agent/qwen_executor.md`。
- Agent先读 `Docs/AI/PROJECT_CONTEXT.en.md` 的路由，再按主题与编号只读五类对应 `.en.md` 段落；原名 `.md` 给开发人员阅读，仅核验翻译或英文缺证据时定向追溯，不例行加载两种语言。
- 收尾时Codex先更新英文任务、验证和必要决策事实，其他外部子Agent（轻量优先Qwen）据本次差异同步中文；同ID、路径、执行身份、轮数、验收与未验边界一致才算同步完成。失败切其他执行者，保留原成果和未完成状态，不凭翻译声称业务验证通过。
- 本节优先于下方历史“查找默认豆包”和无语言后缀的记忆读写说明；中文历史不删除，英文正文是全中文规则的授权例外。文件分版仍只有原五类职责，不新增独立记忆体系。
- 英文以当前有效规则和必要续作事实为精简工作记忆，中文完整保留历史。需要尚未补录的旧编号时，先委派其他子Agent按编号取中文原段并补入对应英文文件，再由Codex读取；不以首次分版全文重译历史作为开工前置，也不假称全部历史已翻译。

## 豆包与WorkBuddy桌面工作任务委派

用户已长期授权本项目任务内的编译、测试、只读查找及允许范围内文件操作权限自动同意。Agent核对原会话真实请求后自动选择“允许本次／Allow／allow_once”，不再让用户手动点击或重复授权；该用户授权优先于Skill通用手动审批说明。界面未显示时通过可用原生接口核对和处理待办，记录结果，沿原任务继续；不得以审批已提交冒充命令执行成功，不扩大任务范围或重复派工。

1. Codex为主Agent，解读需求、设计开发逻辑并发布任务；豆包和WorkBuddy均为开发子Agent，继承 `AGENTS.md` 与对应开发角色约束。使用官方桌面的工作模式／工作任务，项目固定 `LYFMMORGP`、本地目录 `D:/unitypro/LYFMMORGP`，不派普通对话或其他项目。
2. 豆包只经 `E:/doubao-cli/doubao-windows.cmd`，新建和返工明确传 `--runtime local --project 38435310952198914 --workspace D:/unitypro/LYFMMORGP --permission AskOnRisk`；从CLI项目列表及任务上下文核对本项目。桌面工作路径启用原生agent_mode，不传headless专用mode work，不走网页或云电脑网页入口。
3. WorkBuddy按 `workbuddy-executor` Skill 优先经Agent Hub，传 `provider: workbuddy` 与本项目workspace；兼容直连也核对同目录原生工作会话的sessionId。不得使用网关源码目录或历史隔离测试会话。
4. 任务单说明标识、开发角色、分支及基线、逐项文件范围、需求、验收和交付格式。保存豆包conversationId/runId或WorkBuddy Hub/task/session编号，返工沿原任务提供失败证据；已受理超时恢复原任务，不盲目重发。
5. 开发子Agent可直接修改授权本地文件并先自检，Codex主Agent最后核对差异、产物并测试；有明确修正方向时附失败证据、复现步骤和预期结果返回原开发子Agent重新开发或修复，再由Codex复测；确认豆包与WorkBuddy无法解决时按失败回退由Codex接手，不通过不标验收完成。仅交付补丁时本地开发子Agent核对基线落盘；通过后统一记录、集成、提交推送功能分支，不合main。入口不可用如实记录，不回退网页或普通对话。

细则见 `AIconfig/agent/doubao_executor.md`、`AIconfig/agent/workbuddy_executor.md`；本段替换旧网页云电脑委派流程，历史实验不作当前入口。

## 查找与 Bug 排查先豆包后 Codex 核验

1. 代码、参考项目查找或Bug定位默认由Codex限定问题、范围与证据要求，先派豆包执行本项目官方桌面只读工作任务；用户另有明确分工时优先遵从。不同时自行做同范围完整搜索，减少Codex额度消耗。
2. 豆包交付精简查找路线、真实文件路径和行号、关键函数/调用链、结论依据与未确认项；Bug附实际复现、现象或日志。仅查找不得自行改业务或修复。
3. Codex先顺着该路线读取文件并核对证据，执行必要验证；成立后沿用结果，不从头全量重查。路线错误、证据不足或结论不成立时先退原任务补充，只有满足下述两模型各7轮门槛才转Codex独立解题，最终结论仍由Codex负责。
4. 豆包已受理超时恢复原任务，入口不可用按既有桌面规则记录阻断，不伪称成功。后续业务修复仍走开发子Agent和最终验收流程；协作入口读取、约束和记录维护本身无需派查找任务。

## 豆包与 WorkBuddy 的额度节省和失败回退

1. Codex只拆解需求、限定范围和验收；豆包先做只读查找与Bug定位，WorkBuddy根据Codex核验后的路线修改授权文件并自检，Codex只做定向复核、测试和集成。
2. 豆包报告成立后不重复全量搜索；WorkBuddy任务只包含已确认结论和逐项文件，避免两个执行者重复读取整个项目。
3. 同一未解决问题豆包7轮、WorkBuddy7轮，各为首次1轮加返工6轮。未满7轮时必须带失败证据和预期结果退原任务补充/返工，不能因一次失败或自报不能解决提前切GPT。首个模型满7轮仍失败，再让另一个在相同范围补充定位或修复；两者各7轮仍未通过后，Codex才独立查找、设计、实现与验证，提前解决即停止。
4. 回退是本流程“主Agent不直接改业务代码”“必须委派”和“失败退原任务”的明确例外；仍执行范围、中文注释、文件清单、测试、日志、分支、提交和推送要求。等待超时先查原任务真实状态，不当作模型失败；接手修改前确认原执行者结束或停止。
5. 已核验结论引用报告路径和必要摘要，不重复背景与全量扫描；Codex保留关键行为、协议和集成验证，检查通过后不无理由重复扩大测试。
6. 计数为一次实际执行及交付核验，自检/核验/等待/状态查询/连接失败不增加轮数，新会话不清零。交接记模型、问题、任务/会话/轮次ID、当前轮数、结果、失败证据、下一轮要求；工具不可用记阻断并恢复原任务，不凑次数或提前转GPT。用户明确要求提前接手时优先遵从。本节轮数是同一问题按模型计数，与下方审查轮数一致，均按模型分别计数。

### 精简任务单与交付格式

任务单头部附任务标识、项目/目录、分支及基线，正文使用四部分：问题/目标、允许范围、已知证据（含报告路径）、验收条件。WorkBuddy收到已核验结论与文件清单，不重新扫描整个项目。

报告只返回结论、实际文件路径/行号、必要调用链、检查命令及结果、未确认项和报告路径。详细源码、完整日志与原始证据留文件：正式分析归`项目分析/`，修改清单归`项目修改日志/`，临时执行证据归`_temp/`。后续交接直接引用已有报告；不在聊天中粘贴大量源码，也不省略验收所需证据。

### 精简执行与一次必要验收

- 开发者先自检，Codex核对实际差异、关键证据并完成一次必要验收；通过且相关输入未变不重复读取、编译、测试或审计，只有新修改、失败或未解决问题才定向补验。保留必要编译及关键行为、协议、集成验证，不以自报完成代替验收。
- 五类协作入口按类别、主题及唯一任务编号定向读取：先遵守 `AGENTS.md`，读取 `PROJECT_CONTEXT.md` 的 `[DOCS-READ]` 和 `[DOCS-ROUTES]`；用 `rg -n '^## .*\[网络\]' Docs/AI/QUERY_TASKS.md` 等命令定位相关主题标题，再按编号仅读命中段落，读到下一个二级标题前停止。代码/文件任务读 CURRENT_TASK、DECISIONS、TEST_REPORT 的相关标签；查询和方案正文只读 QUERY_TASKS。需要稳定结构时按 PC-080 至 PC-084 定位，不默认整文件或归档全文加载；独立功能仅携带必要上下文，符合自动新开对话规则时按长期授权创建。
- 完整过程集中一份项目修改日志，CURRENT_TASK、TEST_REPORT和其他必要记录只写各自职责的短摘要与引用；Git回执集中该日志，不为回执重复更新全部入口。逐项文件清单、必要决策和真实失败证据仍保留。
- 小修复采用最小必要验证范围，不扩大为大型验证工程；任务单、工具输出和最终回复简短，完整源码及日志留文件。

### 自动新开对话与短交接（2026-10-22）

- 用户长期授权自动新开对话：新需求与之前功能无关联或关联较小，且当前上下文较长时，新建独立对话承接新需求；即使仍是同一功能，上下文过长、出现反复压缩或明显影响任务处理时，也新建对话继续。由Agent判断触发，无需重复询问，用户明确要求留在原对话时优先遵从。
- 创建前先更新CURRENT_TASK和TEST_REPORT的相关短交接；新对话仅携带当前目标、范围、项目目录、当前分支及基线、已核验结论与文件路径、未提交修改范围、待办及外部任务标识和真实轮次，不复制完整旧聊天。保持各7轮计数与原执行任务身份，确认原任务真实状态后续接，避免重复派工或同时写同一文件。
- 使用create_thread创建同项目的本地新对话，先list_projects核对项目；需要精简上下文时采用新建对话，不使用继承全历史的fork_thread。创建成功后给出并打开新对话入口，后续任务由新对话承接，原对话完成交接；创建失败如实记录并保留交接，不能声称已创建或已转移。

## 标准执行流程
1. **解读需求**：Codex主Agent明确用户目标、范围、优先级和验收标准，必要时协调产品经理补充信息。
2. **设计开发逻辑**：Codex主Agent明确业务流程、现有接口、修改文件和任务拆分，必要时采纳策划／架构建议，不扩大用户范围。
3. **发布开发任务**：Codex向对应开发子Agent（含WorkBuddy、豆包）派发任务，指定本项目、分支、基线、文件范围和验收要求。
4. **开发与自检**：子Agent修改授权本地文件并执行自检，交付文件清单、产物和实际结果；协议变更先更新 `LYF_Server/ProtoBuf/proto`。
5. **最后测试与审查**：Codex核对实际文件，执行必要编译、静态检查或运行测试，结合测试／审查角色证据作最终验收，结果写入 `Docs/AI/TEST_REPORT.md`，不只接受子Agent自报完成。
6. **失败退回并复测**：未通过时Codex沿原任务发送失败证据、复现步骤和预期结果，原开发子Agent重新开发或修复并交付，再回第5步；主Agent和审查员不代改业务代码，未通过或受阻如实保留未完成状态。
7. **验收与集成**：测试通过后Codex统一验收、维护协作记录、集成并按功能分支约束提交推送。

## 规则
- **逐项交付文件**：每次代码修改后的回复与 `项目修改日志/` 必须列出新增、修改、移动、删除的文件及各自用途、具体变化；Unity `.meta` 可随对应文件列出，不用功能概括代替清单。
- **功能分支与上传**：当前功能开发在 `codex/feature-development`，后续分支沿 `codex/` 前缀。仅用户明确要求时才合入 `main`，普通开发、提交和推送授权均不含合并授权。检查通过后由主 Agent 检查暂存范围、提交本次任务文件与日志并推送当前功能分支，不混入无关用户改动、不强推；失败如实报告。
- **提交记录**：中文 Git 提交正文包含修改内容、验证结果和日志路径，类型前缀可沿 conventional-commits；项目修改日志记录分支、提交范围及推送结果，最终回复报告提交号与上传状态。
- **UI 融合沿现有模式**：新增或移植界面沿 View、WindowBase、WindowType 和既有 Ctrl 管理窗口，窗口/Widget 负责展示交互、控制器处理业务协议；不另建 UI 管理器或复制参考 Lua 框架。用户只要求界面时，仅接打开、关闭、分页、滚动等必要交互，不顺带实现选项业务效果。正式控件与引用存于预制体，复用本项目字体、层级和视觉资源。
- **项目难点持续沉淀**：遇到特别难实现、难复现、跨模块联动或多次排查与方案取舍的实际问题，参与角色必须提供事实，主 Agent 同步新增或更新 `项目分析/项目难点.md` 对应独立条目；未解决先记现状，后续补结论。记录背景、难点、证据与失败尝试、根因、方案取舍、关键文件、验证边界、未解决事项和面试讲述/追问；不虚构个人贡献、收益或上线结果，已有专题用项目根相对路径引用。任务收尾检查是否已沉淀，不能仅以对话或修改日志代替。
- **连续判断最多三个**：后续新增或修改代码的单个布尔表达式，`&&`、`||` 组合的判断项最多三个，混合或括号合并统计。超过时拆清晰分支或具名条件，保持求值顺序、短路与业务语义；不以换行规避、不新增多余判断，未经用户另行要求不批量改既有代码。开发和审查均遵守。
- **严格执行用户范围**：用户让做什么就做什么；主 Agent 和所有子 Agent 不自行扩功能、不顺带重构、不设计额外框架或未来需求，只做当前要求必需的最小适配。不得以完善性、稳健性或未来用途扩大开发和审查范围。
- **简单业务保持简单**：按当前真实需求实现最短正常流程；无用户要求或已复现故障，不添加额外校验、身份/状态门禁、代次、请求队列、重试、确认等待、多层空值判断或异常包装。现有接口的实际完成结果与必要接入可以处理，不以人为检查阻止正常业务；审查不得因假设情形强加这些机制。
- **参考移植优先照原代码**：用户指定参考项目时，沿用其代码结构、接口、职责和调用时序，仅做当前工程必要的最小接入适配；不得自行扩展功能、通用管理层或防御包装。额外功能由用户明确提出后再实现。
- **按真实需求审查**：先审核参考一致性和简洁性，不为无生产依据的假设重入/极端测试增加快照、代次包装、等待确认、重试或额外状态；已复现的实际问题只作有依据的最小修正。
- **一类一文件**：每个顶级类、接口、枚举和委托必须独立放置在一个同名源文件中；禁止通过聚合文件定义多个业务类型。
- **主 Agent 边界**：默认Codex负责需求、设计、发布任务、最后验收和记录，开发者实现与返工；确认豆包与WorkBuddy无法解决时，按上述失败回退由Codex独立实现和验证。
- **代码委派**：默认业务源代码交由对应开发Agent执行；符合上述失败回退条件时，Codex可接手当前任务业务代码，不扩大范围。
- **强制创建子 Agent**：正常开发先委派本项目桌面开发任务，补丁由开发者核基线落盘；明确符合失败回退条件时不再强制继续委派，Codex独立完成并验收。
- 谁的问题谁修，审查员不代改
- 协议变更必须先改 `LYF_Server/ProtoBuf/proto` 再生成代码和进入开发，禁止先写业务代码后补协议
- 同一未解决问题每个模型最多7轮（首次1轮、返工6轮）；两模型各7轮仍失败才由Codex独立接手，提前通过停止，用户明确提前接手除外
- 代码审查通过前，禁止声明"完成"
- 每项工作开始前遵守 `AGENTS.md` 并按主题与编号取协作记录；代码/文件修改结束后更新 CURRENT_TASK 与 TEST_REPORT。纯查询只更新 QUERY_TASKS；如有正式文档产物，执行入口仅留文件变化/文档检查与查询编号，不重复查询正文。
- 所有项目修改（代码、配置、协议、表格、资源、场景、工具或文档）的修改说明统一写入项目根目录 `项目修改日志/`；项目解析、参考项目分析、架构设计、功能方案和专题使用说明统一写入项目根目录 `项目分析/`；不得在根目录或 `Docs/AI` 散落创建这些文件。
- `Docs/AI/` 仅维护五类协作入口记录，专题分析正文不放在其中；文档引用一律使用项目根目录相对路径。
- 新增或修改业务代码时，开发者必须为类型/接口、函数（含构造函数）、字段、属性、常量、事件、参数及局部变量补充具体中文注释；审查员必须将注释完整性作为代码规范门禁
- 任务结束后，参与角色必须输出变更摘要或分析结论，审查员输出审查结论，二者并存留痕
