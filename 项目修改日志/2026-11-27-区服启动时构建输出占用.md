# 一区启动时旧服务 DLL 被占用

任务编号 `REALM-START-LOCK-20261127`。2026-11-27，Codex 按开发者选择独立修复。本机默认一区现已在后台启动。

## 故障和修复

默认 `LYF_Server/区服部署/启动区服.bat` 使用 Windows PowerShell 5.1 调用同名脚本并传入 `-IncludeShared -ShowConsole`。本次以后台控制台执行同一启动脚本和一区配置，复现退出码 1。当时一区游戏进程均未启动，项目 Redis 正在监听 6380。MSBuild 覆盖旧 `bin/Debug` 中的 `Network.dll`、`MMoRpgCommon.dll` 时，诊断列出持有文件的 `SGuard64.exe`。十次重试后报 `MSB3027`、`MSB3021`，脚本在启动任何游戏服务之前退出。

开发开服现将各工程的编译输出写入 `_temp/realm-build`，每种服务按整套文件的相对路径和内容复用 `_temp/realm-runtime` 下的版本目录。首次尝试在复制完毕后整体重命名目录，Windows 对 MasterServer、GateServer 的目录曾拒绝访问。最终实现直接写入目标版本目录，复制成功后发布完成标记，同一版本的写入由本机互斥锁串行处理。这样重新开服不必覆盖正在使用的二进制。两个 PowerShell 版本曾因默认排序不同，给字节完全一致的游戏服生成不同目录。改用忽略大小写的序数排序后，两个入口对七类服务使用同一套文件。MasterServer 的公共语音缓存及好友语音继续使用原有目录。现有账号、角色和区服配置均沿用原位置。

## 验证结果

- 在原 DLL 仍被占用的开发机上，经默认一区配置启动中心服、登录服、调度服、交易服、MasterServer、两台 GS 和网关，共八个游戏服务进程。TCP 10110、10120、10130、10131、10140、10150、10160、10170 以及网关 UDP 10141 均由预期进程监听。
- 从真实登录端口 10120 发送协议 `11030`，登录服和中心服返回「1区 五域大陆」和 `127.0.0.1:10140`。调度服对 `11300` 返回地图 1 的一线 GS 1、二线 GS 2，两条线路均有已创建的正场景编号。
- 本项目的 `LYF_Server/Redis/redis-server.exe` 在 `127.0.0.1:6380` 通过认证后对 `PING` 返回 `PONG`。
- 临时 XML 使用独立交易和中心端口。交易服 Debug 启停两次并复用同一运行文件，Release 启停一次，无解决方案的模拟部署包从原 bin/Debug 启停一次。四次按区关闭时，真实一区交易服的 PID 始终相同。一区批处理当前调用的关服脚本以拦截停止调用的方式核对匹配范围，得到全部八个一区进程，真实一区继续运行。
- 在独立文件样本中持有旧程序，只改配置即可生成新的版本目录。旧版配置仍可读取，第二次读取新版本复用同一份文件。Windows PowerShell 5.1 与 PowerShell 7 均验证七类服务复用实际正在运行的文件。
- MasterServer 两个目录连接均指向原 `bin/Debug` 的对应目录。原公共录音缓存中的一个文件可见。四份 PowerShell 脚本通过语法解析，提交前通过 `git diff --check`。

此次使用后台入口和协议客户端，没有用 Unity 真人账号进场，也未进行线上部署。完整重开没有对已恢复的真实一区执行强制停服，关服行为在独立交易服实际验证。
