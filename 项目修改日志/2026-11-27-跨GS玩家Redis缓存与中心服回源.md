# 跨 GS 玩家 Redis 缓存与中心服回源

任务编号 `REDIS-ROLE-HANDOFF-20261127`。Codex 独立完成服务端、部署和联测，开发者已批准写入记录。

## 交接与数据归属

普通跨线和组队进本共用角色交接。原 GS 等待自己的保存确认，再经原网关交出角色基础数据、即时血蓝、冷却截止时间、持久版本和实际背包容量。新 GS 异步查询项目 Redis，之后在逻辑线程装载技能、物品、装备、货币与次数。命中后沿现有流程完成属性恢复和网关路由切换。缓存缺失、损坏、版本或容量不符、Redis 不可用时，目标 GS 向 CenterServer 发起一次 EnterWroldReq。中心服保持 MySQL 权威，成功读到两类数据后回填。老交接包未声明版本时直接走现有中心服读取，同一 GS 内继续使用原在线角色。

缓存按中心服全局角色主键和已确认的存档版本寻址。完整二进制值带 SHA-256 完整性摘要，以十分钟为有效期。进本扣次数时，确认事务只改变全量次数的情况下，Redis 原子复用已缓存的技能和背包且替换为已提交的次数。物品或技能同时变化时，从 MySQL 读取新版本。背包扩容独立写库，容量另行核对。副本选哪一台 GS 仍使用控制服维护的节点状态。

## 联测、发现与边界

- 编译服务端解决方案。真实 CenterServer、GateServer、ControlServer、MasterServer、两台 GameServer，以及隔离端口的项目 Redis 5.0.14.1 和本机 MySQL 8.3.0 独立测试库，承载三名无界面协议玩家。两名 GS2 队员在扣除副本次数后直接命中 Redis，与 GS1 本机队员进入同一实例。手动跨 GS 切线命中时未触发额外的中心服查档。
- 删除缓存键、写入截断值分别触发一次回源并获得完整回填。通过实际扩容协议把背包从 81 格扩大到 82 格，物品版本相同也能恢复新容量。技能升级至 2 级后，旧缓存仍然存在，目标 GS 读取了实际的新版本。停止隔离 Redis 后跨 GS 切线成功。
- 首轮实测发现入场保存仅修改次数就使原版本失效，由此接入纯次数缓存更新。旧版 Windows Redis 的标准输入启动方式会提前退出，已改为端口专属的临时配置。将所有 .NET 服务的 DLL 混放在同一测试目录会使 CenterServer 加载到其他服务的依赖版本，验收使用按项目分开的输出目录。测试未连接游戏业务库，未部署线上、未做压力基准，未使用 Unity 真人双客户端。血蓝和冷却沿用已有交接字段，本次没有单独测量带伤和读秒数值。
- 记录与原始证据位于 `_temp/redis-handoff-20261127/build-separate.log`、`live.log`、`release-build.log`、`release-live.log`、`code-tree.json`。用量见同目录的 `usage-summary.json` 与 `context-compactions.json`。难点复盘见 `项目分析/项目难点.md` 的同任务编号。
